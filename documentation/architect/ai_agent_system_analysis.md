## 2. 5대 시스템 레이어 도출

16개 아티클을 관통하는 핵심 패턴을 추출하면, AI 에이전트는 **5개의 독립적이지만 상호 연결된 레이어**로 구성됩니다.

```
┌─────────────────────────────────────────────────────┐
│  Layer 5: 안전성 & 가드레일 (Safety & Guardrails)     │
│  ─ 샌드박싱, 온톨로지, 권한 제어                        │
├─────────────────────────────────────────────────────┤
│  Layer 4: 전문성 & 학습 (Expertise & Learning)        │
│  ─ Skills, SOP 자가학습, 강화학습 최적화                │
├─────────────────────────────────────────────────────┤
│  Layer 3: 메모리 & 컨텍스트 (Memory & Context)        │
│  ─ 장기 메모리 3종, 컨텍스트 엔지니어링, RLM            │
├─────────────────────────────────────────────────────┤
│  Layer 2: 도구 관리 (Tool Management)                 │
│  ─ 선택, 호출, 오케스트레이션, MCP 원시 타입            │
├─────────────────────────────────────────────────────┤
│  Layer 1: 핵심 루프 & 프로토콜 (Core Loop & Protocol)  │
│  ─ Agent Loop, Open Responses, 장기 실행 하네스        │
└─────────────────────────────────────────────────────┘
```

## 3. 레이어별 시스템화 분석

### 🔄 Layer 1: 핵심 루프 & 프로토콜

**관련 아티클**: #5(Agent Loop), #7(Open Responses), #14(장기 실행 에이전트)

#### 시스템화 가능 포인트

**A. Agent Loop 표준 패턴**

모든 에이전트의 심장부인 Agent Loop은 3단계로 단순화됩니다:

```
[사용자 요청] → [프롬프트 구성] → [모델 추론]
                                    ↓
                              텍스트 응답? → [최종 답변] → 턴 종료
                              도구 호출? → [도구 실행] → [결과를 프롬프트에 추가] → 재추론
```

시스템화 원칙:
- **프롬프트 캐싱 최적화**: 새 프롬프트가 이전의 정확한 prefix가 되도록 설계 → 샘플링 비용 linear 유지
- **컨텍스트 윈도우 자동 압축**: 토큰 임계값 초과 시 `/responses/compact` 호출
- **도구 목록 일관된 순서 유지**: 캐시 미스 방지

**B. 장기 실행 에이전트 하네스**

단일 세션을 넘어 며칠간 작업하는 에이전트를 위한 2단계 구조:

```
[Initializer Agent]                    [Coding Agent (매 세션)]
 ├─ 환경 세팅                            ├─ 1. 디렉토리 확인
 ├─ 기능 체크리스트 JSON 생성              ├─ 2. Git 로그 읽기
 │  (200+ 항목, 초기 상태: "실패")         ├─ 3. 진행상황 파일 읽기
 └─ 기본 프로젝트 구조 생성               ├─ 4. 다음 작업 1개 선택
                                         ├─ 5. 구현 + E2E 테스트
                                         ├─ 6. Git 커밋
                                         └─ 7. progress.txt 업데이트
```

시스템화 원칙:
- **한 번에 하나씩**: 기능 1개 완성 → 커밋 → 다음 기능
- **Git = 세션 간 인수인계 도구**: 코드 변경 이력이 곧 문맥
- **버그 우선 수정**: 새 기능 전에 이전 세션 버그부터 해결

**C. API 표준 전환**

Chat Completion → Open Responses로의 전환 핵심:
- sub-agent loops: 제공자 측에서 다단계 처리 후 최종 결과만 반환
- 추론 과정 투명성: `content` (원본) vs `summary` (요약) vs `encrypted_content` (암호화)
- `max_tool_calls`로 반복 횟수 제한

### 🔧 Layer 2: 도구 관리

**관련 아티클**: #1(BEACON), #8(3-Pillar), #16(고급 Tool Use), #6(MCP 원시 타입)

#### 시스템화 가능 포인트

**A. 도구 분류 체계 (3-Pillar Framework)**

모든 도구를 3가지로 분류하면 설계가 명확해집니다:

| 기둥 | 역할 | 위험도 | 예시 |
|------|------|--------|------|
| **Data Access** (읽기) | 정보 수집 | 🟢 낮음 | 벡터DB 검색, SQL 조회, API 호출 |
| **Computation** (처리) | 분석·변환 | 🟡 중간 | 코드 실행, ML 추론, 데이터 변환 |
| **Actions** (실행) | 상태 변경 | 🔴 높음 | 이메일 발송, DB 수정, 결제 처리 |

시스템화 원칙:
- RAG도 Data Access 기둥의 도구 호출일 뿐
- 3기둥이 순환하는 패턴: 데이터 수집 → 계산 → 행동 → 검증(다시 데이터 수집)
- **행동 도구에는 별도 안전장치 필수** (Layer 5와 연결)

**B. 대규모 도구 선택 전략**

도구가 100개를 넘으면 성능 30%+ 하락. 해결책 3가지:

| 전략 | 메커니즘 | 토큰 절약 |
|------|---------|----------|
| **BEACON (계층 탐색)** | 카테고리 → 서브그룹 → 개별 도구 (20→10→5) | 단계적 축소 |
| **Tool Search Tool** | `defer_loading: true`, 온디맨드 검색 | 85% 감소 |
| **Programmatic Tool Calling** | LLM이 Python 코드로 오케스트레이션 | 37% 감소 |

시스템화 원칙:
- 핵심 도구 3~5개만 상시 로드, 나머지는 온디맨드
- 배치 작업은 코드 기반 오케스트레이션으로 전환
- Tool Use Examples로 파라미터 정확도 72%→90% 개선

**C. MCP 프로토콜 설계 원칙**

5가지 원시 타입의 분리 원칙:

```
Roots (범위 정의)
 └── Resources (읽기 전용 데이터) ← 부수 효과 없음
 └── Tools (실행 가능 작업)       ← 부수 효과 있음
 └── Prompts (재사용 지시사항)    ← "무엇을 할지"
 └── Sampling (생성 방식 제어)    ← "어떻게 할지"
```

시스템화 원칙:
- **읽기(Resources)와 실행(Tools) 철저히 분리** → 디버깅·권한 제어 용이
- **지시사항(Prompts)과 생성 방식(Sampling) 분리** → 독립 조정 가능
- Roots로 스코프를 명시적 정의 → 에이전트의 접근 범위 명확화

### 💾 Layer 3: 메모리 & 컨텍스트

**관련 아티클**: #9(RLM), #10(장기 메모리 3종), #11(컨텍스트 엔지니어링)

#### 시스템화 가능 포인트

**A. 3종 장기 메모리 아키텍처**

| 메모리 유형 | 질문 | 저장소 | 활용 |
|-----------|------|--------|------|
| **에피소드 (경험)** | "이전에 무슨 일이 있었나?" | 벡터DB + 타임스탬프 | 사례 기반 추론 |
| **의미론적 (지식)** | "내가 무엇을 아는가?" | 지식 그래프 / 관계형DB | 도메인 전문성 |
| **절차적 (스킬)** | "이걸 어떻게 하는가?" | 워크플로우 / RL 정책 | 자동화된 루틴 |

시스템화 원칙:
- 에피소드 메모리에서 패턴 추출 → 의미론적 메모리로 정제 (일반화)
- 반복 작업은 절차적 메모리로 이동 → 응답 시간 개선 + 계산 오버헤드 감소
- **무엇을 저장할지 선별** 필수: 모든 것 저장 → 컨텍스트 오염

**B. 컨텍스트 엔지니어링 6요소**

프롬프트 엔지니어링(질문 잘하기) < 컨텍스트 엔지니어링(올바른 정보를 적시 제공):

```
[Agents] → 전체 조율
[Query Augmentation] → 애매한 입력을 구조화된 쿼리로
[Retrieval] → 청크 크기 = 정밀도 vs 맥락 균형
[Prompting] → 검색 결과 활용 방법 지시
[Memory] → 단기(현재 대화) + 장기(영구 저장)
[Tools] → 텍스트 세계 밖 실제 행동
```

컨텍스트 실패 4대 패턴 & 대응:

| 실패 패턴 | 증상 | 대응 전략 |
|----------|------|----------|
| **Poisoning (오염)** | 잘못된 정보 재사용 누적 | 검증 단계 추가, 출처 표시 |
| **Distraction (산만)** | 과거 패턴만 반복 | 메모리 압축, 최신 정보 우선 |
| **Confusion (혼란)** | 엉뚱한 도구/문서 선택 | 도구 스코핑, Roots 설정 |
| **Clash (충돌)** | 모순 정보 사이 갈팡질팡 | 출처 우선순위, 온톨로지 정의 |

**C. 초대규모 컨텍스트 처리 (RLM)**

컨텍스트 윈도우를 넘어서는 입력(100배+)을 처리하는 방법:

```
[긴 프롬프트] → Python 변수로 저장 (환경)
                    ↓
            [키워드 필터링] → 정규표현식으로 관련 부분 찾기
                    ↓
            [청크 분할] → 관리 가능한 크기로 분할
                    ↓
            [재귀 호출] → 각 청크에 대해 하위 LM 호출
                    ↓
            [결과 종합] → 변수에 저장 → 최종 답변 생성
```

시스템화 원칙:
- 프롬프트를 "읽을 대상"이 아닌 "탐색할 환경"으로 전환
- 전체를 한 번에 처리 → 선택적으로 필요한 부분만 읽기
- 중앙값 기준 기본 모델보다 저렴, 복잡한 경우 비용 증가

### 🧠 Layer 4: 전문성 & 학습

**관련 아티클**: #4(Anthropic Skills), #15(Skills 역설계), #3(Agent Lightning), #13(Acontext)

#### 시스템화 가능 포인트

**A. Skills = 패키징된 도메인 전문성**

```
skill_name/
├── SKILL.md          ← 핵심 지시사항 (~500 토큰)
├── docs.md           ← 참조 문서 (2,000+ 토큰)
└── apply_template.py ← 재사용 스크립트
```

3단계 Progressive Disclosure:
1. **메타데이터만** (~50 토큰): 이름 + 설명
2. **SKILL.md 로드** (~500 토큰): 해당 Skill 필요 시
3. **참조 문서 로드** (2,000+ 토큰): 추가 세부사항 필요 시

시스템화 원칙:
- Skills는 코드가 아니라 **프롬프트 템플릿** (메타-툴 아키텍처)
- 알고리즘적 라우팅 없음 → 순수 LLM 추론으로 Skill 선택
- 비개발자도 30분 내 첫 Skill 제작 가능 (skill-creator)
- 3가지 유형: Foundational (범용) / Partner (서비스 연결) / Enterprise (내부 지식)

**B. 자가학습 메커니즘 (Acontext)**

```
[저장] Session에 대화, Disk에 산출물
  ↓
[관찰] Task Agent가 백그라운드에서 작업 추적
  ↓    └─ 작업 목록 추출, 진행상황 기록, 사용자 선호도 저장
[학습] 성공한 작업 패턴 → SOP 자동 추출 → Space에 저장
  ↓
[재사용] experience_search로 과거 스킬 검색
```

시스템화 원칙:
- 에이전트가 **경험에서 스스로 SOP를 추출**
- 너무 단순한 작업은 자동 스킵
- 임베딩 검색 + 에이전틱 탐색 이중 모드

**C. 강화학습 기반 비침습적 최적화 (Agent Lightning)**

```
[기존 에이전트 코드] → agl.emit_xxx() 헬퍼 추가
         ↓
[LightningStore] ← 프롬프트, 도구호출, 보상 신호 수집
         ↓
[RL 알고리즘] → 개선된 프롬프트 템플릿 / 정책 가중치 반환
         ↓
[추론 엔진 업데이트]
```

시스템화 원칙:
- 프레임워크 불문 (LangChain, AutoGen, 순수 Python)
- 멀티 에이전트 시스템에서 **특정 에이전트만 선택적 훈련**
- 알고리즘 선택지: RL, 자동 프롬프트 최적화, SFT

### 🛡️ Layer 5: 안전성 & 가드레일

**관련 아티클**: #2(샌드박싱), #12(온톨로지)

#### 시스템화 가능 포인트

**A. 코드 실행 샌드박싱 스펙트럼**

```
[YOLO 모드]                          [매번 권한 확인]
   빠르지만 위험 ←─────────────────→ 안전하지만 느림
                    ↑
            실용적 중간 지대
         bubblewrap / Deno Sandbox
```

| 접근법 | 대상 | 핵심 기능 |
|--------|------|----------|
| **bubblewrap** | 로컬 개발자 | 시스템 읽기전용, 프로젝트만 쓰기 가능, 네트워크 허용 |
| **Deno Sandbox** | 서비스 구축자 | 네트워크 egress 화이트리스트, 시크릿 프록시 주입 |

Deno Sandbox 혁신 2가지:
1. `allowNet`: 승인된 호스트만 접근 허용
2. `secrets`: API 키가 코드에 노출되지 않음 → 승인된 호스트 요청 시에만 프록시가 주입

**B. 온톨로지 기반 비즈니스 가드레일**

```
[비즈니스 개념 정의] → 온톨로지 (단일 진실 공급원)
         ↓
[Neo4j / 트리플스토어] ← 엔티티, 관계, 정책 저장
         ↓
[DocIntel Agent] → 데이터 수집 → 온톨로지 기반 DB 구축
         ↓
[Data Discovery Agent] → 올바른 데이터 검색 + 검증
         ↓
[Business Process Agent] → 정책 준수하며 작업 실행
```

시스템화 원칙:
- "고객", "제품" 같은 동일 용어의 부서별 다른 의미를 **단일 정의로 통일**
- 존재하지 않는 엔티티 생성 시 데이터 발견 단계에서 **환각 자동 감지**
- 공개 온톨로지 활용: FIBO(금융), UMLS(의료)

## 6. 핵심 인사이트 요약

### 반복 출현하는 설계 원칙 (16개 아티클 공통)

1. **Progressive Disclosure**: 한 번에 모든 정보를 주지 않고 필요할 때만 로드 (Skills 50→500→2000+ 토큰, BEACON 1000→20→5개, Tool Search Tool)

2. **읽기와 실행의 명확한 분리**: MCP의 Resources vs Tools, 3-Pillar의 Data Access vs Actions, 온톨로지의 조회 vs 변경

3. **경험의 구조적 축적**: 에피소드 메모리 → 패턴 추출 → 의미론적 지식 → 절차적 스킬 (Acontext SOP, Skills, 절차적 메모리)

4. **기존 도구의 재활용**: Git을 세션 간 인수인계에, Python REPL을 컨텍스트 탐색에, JSON Schema를 도구 검증에 사용

5. **실용적 중간 지대**: YOLO vs 매번 확인 사이의 샌드박싱, 단일 세션 vs 무한 실행 사이의 체크리스트 기반 하네스

### 아직 해결되지 않은 과제

- 멀티 에이전트 역할 분배 최적 기준 (범용 1개 vs 전문 N개)
- 코딩 외 도메인(과학 연구, 금융 모델링)에서의 장기 실행 하네스 검증
- 온톨로지 구축의 초기 비용 대비 ROI 측정
- RLM의 비동기 병렬 처리 구현
- Open Responses의 클라이언트 compliance 테스트 부재
