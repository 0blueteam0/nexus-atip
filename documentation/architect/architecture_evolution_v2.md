# 아키텍처 진화: Compound × Context × Harness Engineering
# Architecture Evolution v2.0: Three Engineering Paradigms Integration

> **진화 방향**: 정적 도구 전환 프레임워크 → 자기 개선·컨텍스트 최적화·신뢰성 거버넌스 시스템
> **통합 패러다임**: Compound Engineering + Context Engineering + Harness Engineering
> **DB 연동**: 7개 데이터베이스 도메인 식별, Triple-Store 동기화 전략

> **버전**: v2.0 | 2026-02-26
> **Article Registry**: #019 Compound Engineering | #020 Context Engineering | #021 Harness Engineering

## 0. Executive Summary

v1.0 아키텍처는 8개 구독제 AI 도구를 3-tier 메모리와 HANDOFF.md 프로토콜로 통합했습니다. v2.0은 여기에 2026년 초 업계 컨센서스로 자리잡은 **세 가지 엔지니어링 패러다임**을 통합하여 아키텍처를 근본적으로 진화시킵니다.

```
┌──────────────────────────────────────────────────────────────────────┐
│                        v2.0 진화 요약                                 │
│                                                                      │
│  v1.0 (현재)              →    v2.0 (진화)                            │
│                                                                      │
│  정적 도구 라우팅           →    컨텍스트 인식 상태 머신 라우팅          │
│  수동 HANDOFF.md           →    progress.json + HANDOFF.md 이중 출력   │
│  일일 워크플로우            →    작업 단위 Compound Loop                │
│  Notion DB 단독            →    Notion + SQLite + Git (Triple-Store)  │
│  수동 메모리 프로모션        →    Solutions DB 기반 자동 프로모션         │
│  사람 리뷰만               →    멀티 에이전트 병렬 리뷰 + 사람 승인      │
│                                                                      │
│  코어 도메인 변경: 0줄 (헥사고날 아키텍처 약속 유지)                     │
└──────────────────────────────────────────────────────────────────────┘
```

핵심적으로 이 세 패러다임은 같은 문제의 **서로 다른 레이어**를 다룹니다. Compound는 "작업이 시스템을 어떻게 개선하는가", Context는 "AI에 무엇을 보여줄 것인가", Harness는 "세션을 어떻게 안정적으로 운영하는가"에 답합니다. 이 세 가지가 합쳐져야 비로소 "시간이 지날수록 AI 지원 작업이 안정적으로 나아지는 시스템"이 완성됩니다.

## 1. 세 가지 엔지니어링 패러다임 분석

### 1.1 Compound Engineering (컴파운드 엔지니어링)

**출처**: Every.to — Cora 팀 (Kieran Klaassen)
**핵심 URL**: https://every.to/guides/compound-engineering

> **핵심 원칙**: "각 작업 단위가 후속 작업을 더 쉽게 만들어야 한다. 더 어렵게 만들어서는 안 된다."

대부분의 코드베이스는 시간이 지나면서 복잡해지는데, 이는 새 기능이 복잡성만 추가하고 시스템에 되돌려주지 않기 때문입니다. Compound Engineering은 이 엔트로피를 **역전**시킵니다. 핵심은 4단계 루프입니다.

```
┌──────────────────────────────────────────────────────────────────────┐
│                     Compound Engineering 메인 루프                     │
│                                                                      │
│     Plan ──→ Work ──→ Review ──→ Compound ──→ (repeat)               │
│     (40%)    (10%)    (30%)      (20%)                               │
│                                                                      │
│  Plan: 요구사항 이해, 코드베이스 연구, 외부 조사, 설계, 검증             │
│  Work: 에이전트가 계획 실행, 개발자가 모니터링                           │
│  Review: 복수 에이전트 병렬 리뷰, P1/P2/P3 우선순위, 수정 및 검증       │
│  Compound: 해결 방법 캡처, 메타데이터 태깅, CLAUDE.md 업데이트, 검증    │
│                                                                      │
│  ★ 4번째 단계(Compound)가 일반 개발과의 차이점.                         │
│    이걸 건너뛰면 "AI 보조 전통적 개발"일 뿐입니다.                      │
└──────────────────────────────────────────────────────────────────────┘
```

**주요 메커니즘:**

Compound Engineering의 플러그인은 **26개 전문화된 에이전트**, **23개 워크플로우 명령**, **13개 스킬**로 구성됩니다. 리뷰 단계에서는 14개 이상의 에이전트가 병렬로 작동하여 보안(security-sentinel), 성능(performance-oracle), 아키텍처(architecture-strategist), 데이터 무결성(data-integrity-guardian) 등을 동시에 검사합니다.

**50/50 규칙**: 엔지니어링 시간의 50%를 기능 개발에, 50%를 시스템 개선에 할당합니다. 시스템 개선이란 리뷰 에이전트 생성, 패턴 문서화, 테스트 생성기 구축 등을 의미합니다. 리뷰 에이전트를 1시간 만드는 것이 향후 1년간 10시간의 리뷰 시간을 절약합니다.

**Solutions Library**: 해결된 모든 문제가 YAML 프론트매터가 달린 검색 가능한 마크다운으로 저장됩니다. `docs/solutions/`에 카테고리별로 정리되어 미래 세션이 과거 해결책을 자동으로 찾을 수 있습니다.

### 1.2 Context Engineering (컨텍스트 엔지니어링)

**출처**: Manus (Yichao "Peak" Ji), Google ADK, Faros AI, 업계 컨센서스
**핵심 URL**: https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus

> **핵심 원칙**: "모델의 입력 품질이 출력 품질을 결정한다. 컨텍스트는 단순히 더 많은 데이터가 아니라, 전략적 입력 설계다."

프롬프트 엔지니어링이 "어떻게 물을 것인가"에 집중한다면, 컨텍스트 엔지니어링은 "무엇을 보여줄 것인가"에 집중합니다. 모델에 데이터, 지식, 도구, 메모리, 구조를 어떻게 제공할지를 시스템으로 설계하는 분야입니다.

**Google ADK의 3대 설계 원칙:**

첫째, **저장(Storage)과 표현(Presentation)을 분리**합니다. 영속적 상태(Sessions)와 호출별 뷰(working context)를 구분하여, 저장 스키마와 프롬프트 포맷을 독립적으로 진화시킬 수 있습니다. 둘째, **명시적 변환(Explicit Transformations)**을 사용합니다. 컨텍스트가 이름이 있는 순서화된 프로세서를 통해 구축되어 "컴파일" 단계가 관찰·테스트 가능해집니다. 셋째, **기본적으로 범위를 제한(Scope by default)**합니다. 모든 모델 호출과 서브 에이전트가 최소 필수 컨텍스트만 봅니다.

**Manus의 6대 실전 원칙 (프레임워크 4차 재작성의 산물):**

```
┌──────────────────────────────────────────────────────────────────────┐
│                    Manus 컨텍스트 엔지니어링 6대 원칙                   │
│                                                                      │
│  1. KV-캐시 중심 설계                                                 │
│     - 프롬프트 프리픽스를 안정적으로 유지                                │
│     - 컨텍스트를 append-only로 구성                                    │
│     - 타임스탬프를 시스템 프롬프트 앞에 넣지 않기                        │
│     - JSON 직렬화의 결정론적 키 순서 보장                               │
│                                                                      │
│  2. 제거하지 말고 마스킹                                               │
│     - 도구를 동적으로 추가/제거하면 KV-캐시 무효화                       │
│     - 대신 토큰 로짓 마스킹으로 도구 선택 제어                           │
│     - 이전 action/observation이 정의 없는 도구 참조 → 모델 혼란          │
│                                                                      │
│  3. 파일 시스템 = 확장 컨텍스트                                        │
│     - 무한 크기, 영속적, 에이전트가 직접 조작 가능                       │
│     - 압축 전략은 항상 복원 가능하게 설계                                │
│     - URL/경로만 보존하면 전체 내용은 언제든 복구                         │
│                                                                      │
│  4. 반복(Recitation)을 통한 주의력 조작                                │
│     - todo.md를 매 단계마다 다시 작성                                   │
│     - 글로벌 계획을 모델의 최근 어텐션 범위에 밀어넣기                    │
│     - "lost-in-the-middle" 문제와 목표 불일치 감소                      │
│                                                                      │
│  5. 오류를 컨텍스트에 보존                                              │
│     - 실패한 액션과 스택 트레이스를 남겨두기                              │
│     - 모델이 암묵적으로 내부 신념을 업데이트                              │
│     - 같은 실수 반복 확률 감소                                          │
│     - 오류 복구야말로 진정한 에이전트 행동의 가장 명확한 지표              │
│                                                                      │
│  6. Few-Shot 함정 회피                                                │
│     - 유사한 action-observation 쌍이 쌓이면 패턴 모방 → 드리프트          │
│     - 직렬화 템플릿, 표현 방식, 포맷에 구조적 변이 도입                   │
│     - 컨텍스트가 균일할수록 에이전트가 취약해짐                           │
└──────────────────────────────────────────────────────────────────────┘
```

### 1.3 Harness Engineering (하네스 엔지니어링)

**출처**: Anthropic (Justin Young), OpenAI (Ryan Lopopolo), Philipp Schmid
**핵심 URL**: https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents

> **핵심 원칙**: "모델은 범용 상품이다. 하네스가 에이전트의 성공과 실패를 결정한다."

Martin Fowler는 "하네스 엔지니어링은 컨텍스트 엔지니어링, 아키텍처 제약, 가비지 컬렉션을 포함한다"고 정리했습니다. 모델을 엔진에 비유하면 하네스는 자동차입니다. 최고의 엔진도 핸들과 브레이크 없이는 쓸모가 없습니다.

**Anthropic의 핵심 발견 — 장기 실행 에이전트의 2대 실패 패턴:**

첫 번째 패턴은 **과도한 시도**입니다. 에이전트가 한 번에 너무 많은 것을 구현하려다 컨텍스트 한계에 도달하고, 다음 세션이 반쯤 구현된 상태에서 추측으로 작업을 이어가야 합니다. 두 번째 패턴은 **조기 완료 선언**입니다. 일부 기능이 구축된 후 에이전트가 주변을 둘러보고 "완료"라고 판단하는 현상입니다.

**Anthropic의 해결 — Initializer/Coding Agent 이중 패턴:**

```
┌──────────────────────────────────────────────────────────────────────┐
│              Anthropic 하네스 패턴: 이중 에이전트 구조                  │
│                                                                      │
│  [첫 번째 세션] Initializer Agent                                     │
│    1. init.sh 스크립트 생성 (개발 서버 실행 방법)                       │
│    2. feature_list.json 생성 (200+ 기능, 모두 passes: false)           │
│    3. claude-progress.txt 초기화 (진행 로그)                           │
│    4. 초기 git commit                                                 │
│                                                                      │
│  [후속 세션들] Coding Agent                                           │
│    1. pwd로 작업 디렉토리 확인                                         │
│    2. git log와 progress 파일로 현재 상태 파악                          │
│    3. feature_list.json에서 최우선 미완료 기능 선택                     │
│    4. 한 번에 하나의 기능만 작업 (점진적 진행)                           │
│    5. 브라우저 자동화 도구로 end-to-end 테스트                          │
│    6. git commit + progress 업데이트로 세션 마무리                      │
│                                                                      │
│  ★ feature_list.json은 JSON 사용 (Markdown보다 실수로 덮어쓸 확률↓)    │
│  ★ 에이전트는 passes 필드만 변경 가능, 기능 설명 수정/삭제 불가           │
└──────────────────────────────────────────────────────────────────────┘
```

**OpenAI의 Harness Engineering 실증:**

OpenAI 내부 실험에서 3명의 엔지니어가 Codex를 활용하여 5개월간 약 **100만 줄**의 프로덕션 코드를 1,500개 PR로 생산했습니다 (엔지니어당 하루 평균 3.5 PR). 핵심은 스캐폴딩, 피드백 루프, 문서, 아키텍처 제약을 **기계 판독 가능한 아티팩트**로 인코딩한 것입니다. 의존성은 Types → Config → Repo → Service → Runtime → UI 순서로 흐르며, 구조적 테스트가 계층 위반을 방지합니다.

**Philipp Schmid의 3대 가이드라인:**

첫째, **단순하게 시작**(거대한 제어 흐름 X, 견고한 원자적 도구 제공). 둘째, **삭제 가능하게 빌드**(새 모델이 기존 로직을 대체할 수 있도록 모듈화). 셋째, **하네스가 곧 데이터셋**(에이전트 궤적을 캡처하여 다음 이터레이션의 학습 데이터로 활용).

### 1.4 패러다임 수렴 맵

세 패러다임은 경쟁 관계가 아니라 **상호 보완적 레이어**입니다. 다음 표는 각 패러다임의 기여가 아키텍처의 어느 레이어에 해당하는지를 매핑합니다.

```
┌──────────────┬──────────────────────┬──────────────────────┬──────────────────────┐
│    Layer     │    Compound          │    Context           │    Harness           │
├──────────────┼──────────────────────┼──────────────────────┼──────────────────────┤
│ Planning     │ Plan 단계 +          │ 컨텍스트 윈도우       │ Initializer 에이전트  │
│              │ 리서치 에이전트       │ 설계·범위 결정        │ 환경 셋업             │
├──────────────┼──────────────────────┼──────────────────────┼──────────────────────┤
│ Execution    │ Work 단계 +          │ KV-캐시 인식          │ 점진적 진행 +         │
│              │ 격리된 실행           │ append-only 컨텍스트  │ 커밋 기반 진행        │
├──────────────┼──────────────────────┼──────────────────────┼──────────────────────┤
│ Quality      │ 14+ 병렬 리뷰        │ 오류 보존으로         │ feature_list.json    │
│              │ 에이전트             │ 학습 촉진             │ pass/fail 추적        │
├──────────────┼──────────────────────┼──────────────────────┼──────────────────────┤
│ Learning     │ Compound 단계        │ 파일시스템 =          │ progress 파일 +       │
│              │ (솔루션 라이브러리)    │ 외부화된 메모리       │ git 히스토리          │
├──────────────┼──────────────────────┼──────────────────────┼──────────────────────┤
│ Memory       │ CLAUDE.md =          │ 3-tier 저장           │ 세션 상태             │
│              │ 살아있는 설정         │ 분리                  │ 브리징               │
├──────────────┼──────────────────────┼──────────────────────┼──────────────────────┤
│ Orchestration│ 태스크 라우팅         │ 도구 마스킹           │ 라이프사이클 훅 +     │
│              │ 매트릭스             │ 상태 머신             │ 재시도 로직           │
├──────────────┼──────────────────────┼──────────────────────┼──────────────────────┤
│ DB 필요      │ 솔루션 패턴 DB       │ 컨텍스트 레지스트리   │ 세션 상태 +           │
│              │                      │ + 메트릭 DB           │ 궤적 DB              │
└──────────────┴──────────────────────┴──────────────────────┴──────────────────────┘
```

## 2. 아키텍처 진화: v1.0 → v2.0

### 2.1 변경 사항 요약

```
┌──────────────────┬──────────────────────────┬───────────────────────────────────┐
│    Component     │    v1.0 (현재)            │    v2.0 (진화)                    │
├──────────────────┼──────────────────────────┼───────────────────────────────────┤
│ 메인 루프         │ Morning Boot →           │ Plan → Work → Review → Compound  │
│                  │ Tool Work → Evening Sync │ (작업 단위 루프)                   │
├──────────────────┼──────────────────────────┼───────────────────────────────────┤
│ 컨텍스트 관리     │ HANDOFF.md 수동 복사      │ Context Pipeline                 │
│                  │                          │ (Gather/Scope/Format 3단계)       │
├──────────────────┼──────────────────────────┼───────────────────────────────────┤
```

### 2.2 변경되지 않는 것들 (코어 도메인)

헥사고날 아키텍처의 핵심 약속은 v2.0에서도 유지됩니다. 다음 항목들은 **불변**입니다.

이 목록에는 헥사고날 포트-앤-어댑터 분리 원칙, `.ai/` 디렉토리 구조의 정규 파일 시스템 역할, 마크다운이라는 범용 인터페이스 포맷, Git의 버전 백본 역할, 간접 참조 패턴(CLAUDE.md가 .ai/를 가리킴), 8개 구독 AI 도구와 어댑터 인터페이스, 그리고 구독 취소 시 우아한 성능 저하를 보장하는 Null Adapter 패턴이 포함됩니다.

**즉, 코어 변경 0줄입니다.** 모든 v2.0 추가 사항은 어댑터 레이어와 횡단 관심사(cross-cutting concern) 레이어에서만 발생합니다.

## 3. Compound Loop 통합

### 3.1 진화된 태스크 루프

v1.0의 일일 워크플로우(Morning Boot → Tool Work → Evening Sync)는 **작업 단위(task-level) Compound Loop**로 대체됩니다. 5분짜리 버그 수정이든 3일짜리 기능 개발이든 동일한 4단계를 거치며, 시간 배분만 달라집니다.

```
┌──────────────────────────────────────────────────────────────────────┐
│                    v2.0 태스크 루프 (Compound Loop)                   │
│                                                                      │
│  ┌─────────────────────────────────────────────────────────┐         │
│  │                                                         │         │
│  │   PLAN (40%)                                            │         │
│  │   - 코드베이스 패턴 조사 + 외부 모범 사례 조사            │         │
│  │   - 영향 파일 포함한 솔루션 설계                          │         │
│  │   - 계획 완전성 검증                                     │         │
│  │   - .ai/memory/mid-term/plans/에 계획 기록               │         │
│  │   - DB: Notion Task Log DB에 status=planned 기록         │         │
│  │                                                         │         │
│  │            ↓                                             │         │
│  │                                                         │         │
│  │   WORK (10%)                                            │         │
│  │   - 지정된 AI 도구로 계획 실행                            │         │
│  │   - 변경마다 검증 실행                                    │         │
│  │   - progress.json에 진행 추적 (Harness 패턴)              │         │
│  │   - 서술적 메시지로 점진적 커밋                            │         │
│  │   - DB: Task Log status=in-progress, Tool Analytics 기록  │         │
│  │                                                         │         │
│  │            ↓                                             │         │
│  │                                                         │         │
│  │   REVIEW (30%)                                          │         │
│  │   - 보조 AI 도구로 교차 검증                              │         │
│  │   - 발견사항 P1/P2/P3 우선순위 지정                       │         │
│  │   - P1 즉시 해결                                         │         │
│  │   - 컨텍스트 보존을 위한 오류 패턴 캡처                    │         │
│  │   - DB: Notion Issues DB에 심각도+해결상태 기록            │         │
│  │                                                         │         │
│  │            ↓                                             │         │
│  │                                                         │         │
│  │   COMPOUND (20%)  ← 이 단계가 핵심 차별점                 │         │
│  │   - 무엇이 효과적이었고 무엇이 아니었는지 캡처              │         │
│  │   - YAML 프론트매터로 태깅 (검색 가능성)                   │         │
│  │   - 패턴이 재사용 가능하면 .ai/memory/long-term/ 업데이트  │         │
│  │   - CLAUDE.md/AGENTS.md에 새 학습 반영                    │         │
│  │   - DB: Solutions DB에 카테고리·태그·링크 아티클과 함께 기록│         │
│  │   - 시스템이 다음에 자동으로 이를 잡아낼 수 있는지 검증     │         │
│  │                                                         │         │
│  └──────────────── (다음 태스크로 반복) ──────────────────────┘         │
└──────────────────────────────────────────────────────────────────────┘
```

### 3.2 50/50 규칙 적용

Compound Engineering의 지침에 따라 엔지니어링 시간의 절반을 기능 개발에, 절반을 시스템 개선에 할당합니다. 우리의 멀티 AI 환경에서 시스템 개선이란 `.ai/prompts/` 프롬프트 개선, 효과 데이터 기반 도구 라우팅 가중치 조정, 실제 전환 마찰을 반영한 HANDOFF.md 템플릿 개선, 도구별 전문 리뷰 체크리스트 작성, 미래 세션이 발견할 수 있는 compound 솔루션 구축을 포함합니다. 이 비율은 Tool Analytics DB에서 추적하여 시간 경과에 따른 균형 유지를 보장합니다.

## 4. Context Pipeline 아키텍처

v2.0의 가장 중요한 아키텍처 추가는 **Context Pipeline**입니다. Google ADK의 "저장과 표현 분리" 원칙과 Manus의 캐시 최적화 실전 경험에서 영감을 받았습니다. 구독형 도구 환경에서 KV-캐시를 직접 제어할 수는 없지만, 각 도구에 컨텍스트를 준비하는 방식에 동일한 원칙을 적용할 수 있습니다.

## 5. Harness Layer: 세션 거버넌스

Harness Layer는 각 AI 도구 세션의 시작, 진행, 종료를 관할합니다. Anthropic 연구에 따르면 구조화된 세션 관리 없이는 에이전트가 한 번에 너무 많이 시도하거나, 조기에 완료를 선언하거나, 환경을 깨진 상태로 남깁니다. Claude Desktop에서 Claude Code로, 다시 ChatGPT로 컨텍스트를 넘기는 우리 환경도 동일한 문제에 직면합니다.

### 5.1 구독형 도구의 이중 페이즈 패턴

Anthropic의 initializer/coding agent 패턴을 멀티 도구 환경에 적응시킵니다. 동일 모델에 두 개의 다른 프롬프트를 쓰는 대신, 각 도구 세션 내에서 **두 가지 페이즈**를 구현합니다.

```
┌──────────────────────────────────────────────────────────────────────┐
│              구독형 도구 세션 — 이중 페이즈 패턴                        │
│                                                                      │
│  ┌──────────────────────────────────────────────────────┐            │
│  │ Phase 1: ORIENTATION (세션 첫 2분)                     │            │
│  │                                                       │            │
│  │  1. progress.json 읽기 → 현재 상태 파악                │            │
│  │  2. git log --oneline -20 → 최근 작업 이력 확인        │            │
│  │  3. 기존 작업물 기본 건강 검사                          │            │
│  │  4. feature_list.json에서 최우선 미완료 작업 식별        │            │
│  │  5. 환경이 깨져 있으면 → 새 작업 전에 기존 버그 수정    │            │
│  │                                                       │            │
│  │  ★ "현황 파악" 단계 — Anthropic이 시간 낭비를            │            │
│  │    방지하기 위해 발견한 핵심 단계                        │            │
│  └──────────────────┬───────────────────────────────────┘            │
│                     ▼                                                │
│  ┌──────────────────────────────────────────────────────┐            │
│  │ Phase 2: INCREMENTAL PROGRESS (나머지 세션)            │            │
│  │                                                       │            │
│  │  1. 한 번에 정확히 하나의 기능/태스크만 작업             │            │
│  │  2. 의미 있는 변경 후마다 서술적 메시지로 커밋           │            │
│  │  3. progress.json 업데이트 (완료/잔여/다음)             │            │
│  │  4. 세션 종료 전 표준 형식으로 HANDOFF.md 생성           │            │
│  │  5. 절대 반-구현(half-implemented) 상태로 남기지 않기    │            │
│  │                                                       │            │
│  │  ★ progress.json은 HANDOFF.md에서 생성                 │            │
│  │    (ad-hoc 작성이 아님)                                │            │
│  └──────────────────────────────────────────────────────┘            │
└──────────────────────────────────────────────────────────────────────┘
```

### 5.2 세션 상태 영속화

v1.0의 HANDOFF.md에서 진화한 핵심은 **DB로 영속되는 구조화된 세션 상태**입니다. 모든 세션이 세 가지 아티팩트를 생성합니다.

**progress.json**: 완료 태스크, 현재 태스크, 블로커, 환경 상태를 포함하는 기계 판독 가능한 세션 상태입니다. Session State DB로 동기화됩니다. 핵심 개선점은 이 데이터가 **쿼리 가능**하다는 것입니다. "지난 주 디버깅 태스크에 가장 효과적이었던 도구는?"이라는 질문에 프로그래밍적으로 답할 수 있습니다.

**HANDOFF.md**: 다음 도구나 세션을 위한 사람 판독 가능한 내러티브입니다. 이전과 동일하게 `.ai/memory/handoff/`에 유지되지만, 이제 progress.json으로부터 **생성**됩니다 (ad-hoc 작성이 아님).

**Git commit**: 검색 가능한 히스토리 역할을 하는 서술적 커밋 메시지입니다. git log가 orientation의 추가 컨텍스트 소스가 됩니다.

## 6. 데이터베이스 요구사항 및 통합 아키텍처

### 6.1 7개 데이터베이스 도메인

진화된 아키텍처 분석 결과 **7개** 고유한 데이터 도메인이 구조화된 쿼리 가능 저장소를 필요로 합니다. 기본 원칙은 모든 운영 데이터 흐름이 최소 하나의 데이터베이스를 통과해야 한다는 것으로, 임시 파일로만 존재하는 데이터가 없도록 합니다.

```
┌──────┬──────────────────┬──────────────┬──────────────────┬──────────┬──────────────┐
│  #   │   DB 도메인       │  주 저장소    │  동기 대상        │  출처    │  업데이트 빈도 │
├──────┼──────────────────┼──────────────┼──────────────────┼──────────┼──────────────┤
│ DB-1 │ Solutions Library│ Notion DB    │ SQLite + .ai/    │ Compound │ Compound 단계│
│ DB-2 │ Context Registry │ Notion DB    │ SQLite           │ Context  │ 세션 시작시   │
│ DB-3 │ Session State    │ SQLite       │ Git + Notion     │ Harness  │ 세션 종료시   │
│ DB-4 │ Tool Analytics   │ Notion DB    │ SQLite           │ 3개 모두 │ 태스크 완료시 │
│ DB-5 │ Feature Tracking │ Git (JSON)   │ Notion DB        │ Harness  │ 기능 변경시   │
│ DB-6 │ Review Findings  │ Notion DB    │ GitHub Issues    │ Compound │ 리뷰 주기마다 │
│ DB-7 │ Article Registry │ Notion DB    │ Git + Obsidian   │ Compound │ 새 아티클마다 │
└──────┴──────────────────┴──────────────┴──────────────────┴──────────┴──────────────┘
```

### 6.2 주요 DB 스키마

**DB-1: Solutions Library** — Compound 단계를 직접 활성화하는 가장 중요한 새 데이터베이스입니다. 해결된 모든 문제, 발견된 패턴, 검증된 접근법이 구조화된 메타데이터와 함께 솔루션 레코드로 캡처됩니다. Notion DB 스키마 필드는 다음과 같습니다: category(architecture, coding, debugging, testing, integration, operations), tags(키워드 배열), problem description, solution description, linked articles(Article Registry와의 관계), linked ADRs, tool used, effectiveness score(1-5, 시간 경과에 따라 업데이트), date created, times referenced(자동 증가 카운터). 이 카운터가 3을 초과하면 장기 메모리 프로모션 대상으로 플래그되어 v1.0의 수동 프로모션 규칙을 대체합니다.

**DB-2: Context Registry** — 어떤 컨텍스트 항목이 존재하는지, 얼마나 최신인지, 태스크 유형별 관련도 점수를 추적합니다. Context Pipeline의 scoping 단계가 각 세션에 대해 최소 효과 컨텍스트를 자동 선택할 수 있게 합니다. 관련도 점수는 처음에 수동으로 설정되지만, Tool Analytics 데이터에 기반하여 시간이 지나면서 진화합니다.

**DB-3: Session State** — 각 도구 세션의 기계 판독 가능한 상태를 캡처하여 Harness Layer의 orientation 페이즈가 자유 텍스트 파일을 파싱하지 않고 관련 컨텍스트를 빠르게 로드할 수 있게 합니다. 빠른 로컬 쿼리를 위해 주로 SQLite에 저장되며, 크로스 디바이스 접근을 위해 Notion으로 주기적 동기화합니다.

**DB-4: Tool Analytics** — 데이터 기반 라우팅 결정을 가능하게 하여, 정적 라우팅 매트릭스를 실제 성능에 기반하여 진화하는 것으로 대체합니다. 예를 들어 AMP Code가 리팩토링 태스크에서 Claude Code보다 지속적으로 높은 점수를 받으면 라우팅 매트릭스가 자동 조정됩니다. 50/50 규칙 준수도 여기서 추적합니다.

## 7. 진화된 헥사고날 아키텍처

### 7.1 코어 도메인 (불변, 내부 확장)

**Agent Loop Engine**: 이제 Harness Layer의 관할 하에 initializer/worker 페이즈, 점진적 진행 강제, 세션 상태 영속화가 적용됩니다.

**Context Engine**: HANDOFF.md 프로토콜이 progress.json + HANDOFF.md 이중 출력으로 업그레이드됩니다. Context Registry DB가 자동 scoping을 가능하게 합니다.

## 10. 구현 로드맵: v2.0 추가 사항

v1.0 기반(Week 1-2) 위에 점진적으로 구현하며, Compound Engineering의 원칙(시스템 개선이 시간에 따라 복리로 축적)을 따릅니다. 각 단계가 즉각적 가치를 생산하면서 전체 통합 시스템을 향해 빌드합니다.

**Phase A: Compound Loop (Week 3)**

Day 1-2에 `.ai/memory/solutions/` 디렉토리와 YAML 프론트매터 스키마가 포함된 SOLUTION_TEMPLATE.md를 생성합니다. Day 3-4에 Solutions Library Notion DB를 모든 스키마 필드와 함께 설정하고 Claude Desktop에서 MCP 쿼리 접근을 검증합니다. Day 5에 세 가지 실제 태스크에 대해 4단계 루프를 연습하고, 첫 솔루션들을 캡처하며, compound 단계가 검색 가능하고 태그된 지식을 생산하는지 검증합니다.

**Phase B: Context Pipeline (Week 4)**

Day 1-2에 `.ai/context/` 디렉토리를 scoping-rules.json 및 도구별 포맷 템플릿과 함께 생성합니다. Day 3-4에 Context Registry Notion DB를 설정하고 기존 .ai/ 파일에 대한 초기 관련도 점수를 채웁니다. Day 5에 세 번의 도구 전환에 대해 컨텍스트 컴파일을 테스트하고, v1.0 대비 컨텍스트 크기 감소를 측정합니다 (목표: 40% 감소, 동일 효과).

**Phase C: Harness Layer (Week 5)**

Day 1-2에 `.ai/harness/` 디렉토리를 feature_list.json, orientation.md, review-agents.md와 함께 생성합니다. Day 3-4에 Session State DB용 SQLite 스키마를 생성하고 세션 종료 시 progress.json 생성을 구현합니다. Day 5에 세 가지 다른 도구에서 이중 페이즈 세션 패턴(orientation + incremental progress)을 연습하고, 세션 상태 영속 및 복구를 검증합니다.

**Phase D: DB 통합 & 동기화 (Week 6)**

Day 1-3에 나머지 Notion DB들(Tool Analytics, Feature Tracking, Review Findings)을 설정하고 7개 도메인 테이블 전부가 포함된 SQLite schema.sql을 생성합니다. Day 4-5에 triple-store 동기화 스크립트를 구현하고(Git을 백본으로) 장애 조건(Notion 불가용, SQLite 불가용)에서 동기화를 테스트하며 우아한 성능 저하를 검증합니다.

**Phase E: 피드백 & 최적화 (Week 7-8)**

Week 7에 5영업일간 전체 v2.0 워크플로우를 실행하고, Tool Analytics 데이터를 수집하며, 실증적 성능에 기반한 라우팅 매트릭스 조정을 식별합니다. Week 8에 Solutions Library의 품질과 검색 가능성을 리뷰하고, 실제 사용 패턴에 기반한 컨텍스트 scoping 규칙을 조정하며, 50/50 규칙 할당을 미세 조정하고, 운영 학습을 compound 솔루션으로 문서화합니다.

## 12. 결론

v1.0에서 v2.0으로의 진화는 Multi-AI Subscription Architecture를 정적 도구 전환 프레임워크에서 **자기 개선·컨텍스트 최적화·신뢰성 거버넌스 시스템**으로 변환합니다.

세 가지 엔지니어링 패러다임은 동일한 근본 과제의 서로 다른 레이어를 다룹니다. Compound Engineering은 우리가 완료하는 모든 태스크가 시스템에 재사용 가능한 무언가를 가르치도록 보장합니다. Context Engineering은 각 AI 도구가 정확히 필요한 정보만, 더도 덜도 아닌 양만큼 받도록 보장합니다. Harness Engineering은 세션이 깨끗하게 시작하고, 점진적으로 진행하며, 다음 세션을 위한 구조화된 아티팩트로 끝나도록 보장합니다. 이 셋이 함께 **선순환 사이클**을 만듭니다. 더 나은 컨텍스트 → 더 나은 작업 → 더 나은 솔루션 → 더 나은 컨텍스트.

7개 데이터베이스 도메인은 모든 운영 데이터가 임시 파일로만 존재하지 않고 구조화된 쿼리 가능 저장소를 통과하도록 보장합니다. Triple-Store 전략(Notion, SQLite, Git)은 아키텍처의 핵심 호환성 원칙을 유지합니다. Git 기반 `.ai/` 파일이 8개 도구 전체에서 보편적으로 접근 가능한 상태를 유지하면서, Notion과 SQLite가 접근 가능한 도구를 위한 쿼리 최적화 뷰를 제공합니다.

가장 중요하게, 모든 v2.0 추가 사항이 **코어 변경 0줄**의 호환성 검증을 통과합니다. 모든 새 컴포넌트가 개별적으로 롤백 가능합니다. 헥사고날 아키텍처의 약속이 유지됩니다. 코어 도메인은 불변이고, 시스템은 어댑터 추가와 횡단 관심사 오버레이를 통해서만 진화합니다. 이것이 바로 아키텍처가 스스로에게 복리로 축적되는 것 — 철학이 처방한 그대로입니다.
