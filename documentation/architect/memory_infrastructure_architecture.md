## 1. 장기 메모리 (Long-Term Memory): 서비스 상세 설계

장기 메모리는 프로젝트가 끝나도, AI 도구를 바꿔도, 팀원이 바뀌어도 **살아남아야 하는 지식**입니다. 따라서 특정 도구에 종속되지 않는 서비스에 저장합니다.

### 1.1 GitHub Private Repository — "진실의 단일 원천"

GitHub가 장기 메모리의 **마스터 저장소**인 이유는 세 가지입니다. 첫째, 모든 코딩 도구(Claude Code, Codex CLI, Gemini CLI, AMP Code)가 Git 레포를 네이티브로 읽습니다. 둘째, 버전 히스토리가 자동으로 쌓여서 "언제 무엇이 왜 바뀌었는지"를 추적할 수 있습니다. 셋째, `.ai/` 디렉토리 구조 자체가 코드와 함께 버전 관리되므로 메모리의 변경 이력이 코드의 변경 이력과 자연스럽게 연결됩니다.

```
GitHub Repo: ai-agent-memory (Private)
│
├── .ai/
│   ├── memory/
│   │   └── long-term/
│   │       ├── ARCHITECTURE.md          ← 헥사고날 아키텍처 원칙·설계 헌법
│   │       ├── DOMAIN_KNOWLEDGE.md      ← 비즈니스 도메인 지식
│   │       ├── CONVENTIONS.md           ← 코딩 컨벤션 + AI 프롬프팅 규칙
│   │       ├── DECISIONS.md             ← ADR 누적 기록 (전체 이력)
│   │       ├── ARTICLE_REGISTRY.md      ← 18+ 아티클 누적 레지스트리
│   │       ├── TOOL_PROFILES.md         ← 8개 AI 도구 특성·역할 정의
│   │       └── INTEGRATION_PATTERNS.md  ← 도구 통합 패턴 라이브러리
│   │
│   └── prompts/
│       ├── system-base.md               ← 모든 도구 공통 시스템 프롬프트
│       ├── architect-role.md            ← "당신은 아키텍처 설계자입니다..."
│       └── designer-role.md             ← "당신은 시스템 디자이너입니다..."
│
├── CLAUDE.md      ← Claude Code 자동 로드 → .ai/ 참조 지시
├── AGENTS.md      ← Codex CLI 자동 로드 → .ai/ 참조 지시
├── AGENT.md       ← AMP Code 자동 로드 → .ai/ 참조 지시
└── GEMINI.md      ← Gemini CLI 설정 → .ai/ 참조 지시
```

**갱신 주기**: 주 1회 ~ 월 1회. 중대한 아키텍처 변경이나 새 아티클 추가 시에만 갱신합니다. 모든 변경은 Git commit으로 기록되므로 "왜 이 원칙이 바뀌었는지"를 항상 추적할 수 있습니다.

**각 도구에서의 접근**: Claude Code, Codex CLI, Gemini CLI, AMP Code는 레포 루트의 전용 파일(CLAUDE.md 등)을 세션 시작 시 자동으로 읽습니다. 이 파일들이 `.ai/memory/long-term/`을 참조하도록 작성하면, 어떤 코딩 도구를 열든 동일한 장기 지식에 접근하게 됩니다. Claude Desktop과 ChatGPT에는 해당 파일을 프로젝트에 첨부하거나 업로드합니다. NotebookLM에는 소스로 업로드합니다.

### 1.2 Notion Database — "구조화된 지식 관리"

GitHub의 마크다운 파일은 "내용"을 담지만, Notion 데이터베이스는 그 내용에 **구조와 메타데이터**를 입힙니다. 아티클 레지스트리를 예로 들면, GitHub에는 마크다운 테이블로 존재하지만 Notion에서는 필터링·정렬·관계 연결이 가능한 데이터베이스로 존재합니다.

```
Notion Workspace: AI Agent Hub
│
├── 📊 아티클 레지스트리 DB
│   ├── 속성: #번호, 제목, URL, 날짜, 키워드[], 아키텍처 반영위치, 상태
│   ├── 뷰: 전체 목록 / 컴포넌트별 필터 / 시간순 타임라인
│   └── 관계: → ADR DB (어떤 아티클이 어떤 결정을 유발했는지)
│
├── 📊 ADR (Architecture Decision Record) DB
│   ├── 속성: ADR#, 결정, 근거, 트레이드오프, 상태, 관련 아티클[]
│   ├── 뷰: 활성 결정 / 폐기 결정 / 컴포넌트별
│   └── 관계: → 아티클 DB, → 도구 프로파일 DB
│
├── 📊 도구 프로파일 DB
│   ├── 속성: 도구명, 제공사, 구독플랜, 월비용, 역할, 한도, 상태
│   ├── 뷰: 활성 도구 / 비용 요약 / 역할별 그룹
│   └── 관계: → 태스크 로그 DB
│
├── 📊 도메인 온톨로지 DB
│   ├── 속성: 개념, 정의, 상위개념, 하위개념[], 관련 도구[]
│   └── 뷰: 계층 구조 / 검색
│
└── 📄 아키텍처 문서 페이지들
    ├── 헥사고날 아키텍처 전체 설명
    ├── 포트·어댑터 계약 목록
    └── 호환성 매트릭스
```

**Notion을 쓰는 이유**: Claude Desktop이 이미 Notion MCP 서버와 연결되어 있습니다. Claude Desktop에서 "아티클 레지스트리에서 Context Engine 관련 항목을 찾아줘"라고 하면 Notion DB를 직접 쿼리할 수 있습니다. 이것이 마크다운 파일만으로는 불가능한, 구조화된 메모리 검색입니다.

**GitHub↔Notion 동기화**: 장기 메모리의 "마스터"는 GitHub입니다. Notion은 GitHub의 마크다운을 구조화된 뷰로 보여주는 "프레젠테이션 레이어"입니다. 중대한 변경은 GitHub에서 먼저 커밋하고, Notion DB는 주기적으로 동기화합니다. Notion의 자동화(Custom Agents)를 활용하면 GitHub 커밋 알림 → Notion DB 갱신을 반자동화할 수 있습니다.

### 1.3 Obsidian Vault — "개인 지식 그래프"

GitHub과 Notion이 "팀/시스템 수준"의 장기 메모리라면, Obsidian은 **개인 수준의 지식 그래프**입니다. 연구 과정에서 떠오른 아이디어, 아티클 간의 비공식적 연결, 아직 확정되지 않은 가설 같은 것들이 여기에 살아 있습니다.

```
Obsidian Vault: ai-knowledge (Git 동기화)
│
├── 📁 Research/
│   ├── AI-Agent-Architecture/        ← 아키텍처 관련 연구 노트
│   ├── Memory-Systems/               ← 메모리 시스템 연구
│   └── Tool-Evaluations/             ← AI 도구 평가 기록
│
├── 📁 Ideas/
│   ├── 미확정 아키텍처 아이디어들
│   └── "이런 도구가 있으면 좋겠다" 목록
│
├── 📁 Daily/
│   └── YYYY-MM-DD.md                 ← 일일 작업 로그 (중기로 승격 후보)
│
└── 📁 Templates/
    ├── article-analysis.md           ← 새 아티클 분석 템플릿
    └── tool-evaluation.md            ← 새 도구 평가 템플릿
```

**Obsidian을 쓰는 이유**: 로컬 마크다운 파일이라 모든 AI 도구에 직접 전달할 수 있고, Git 플러그인으로 GitHub과 동기화됩니다. 가장 중요한 것은 **그래프 뷰**로 지식 간의 연결을 시각화할 수 있다는 점입니다. "Google의 Nested Learning 개념이 우리 Memory Manager의 Continuum Memory와 어떻게 연결되는가" 같은 관계를 링크([[]])로 표현하고 그래프로 탐색합니다.

**Git 동기화 설정**: Obsidian Git 플러그인을 설치하고, 자동 커밋(5분 간격)을 설정합니다. Obsidian Vault 자체가 GitHub 레포이므로, 다른 기기에서도 접근 가능하고 버전 히스토리가 자동으로 쌓입니다.

## 2. 중기 메모리 (Mid-Term Memory): 서비스 상세 설계

중기 메모리는 "이번 주 ~ 이번 달"의 활성 작업 맥락입니다. 장기 메모리보다 자주 바뀌지만, 단기 메모리보다 오래 삽니다.

### 2.1 Notion Project Boards — "작업 상태 대시보드"

```
Notion: AI Agent Hub → Projects 섹션
│
├── 📊 태스크 로그 DB
│   ├── 속성: 날짜, 시간, 사용도구, 작업내용, 결과, 다음단계, 상태
│   ├── 뷰: 오늘 / 이번 주 / 도구별 / 상태별
│   └── 자동화: 도구 전환 시 → Notion Agent가 자동 기록
│
├── 📊 스프린트 보드
│   ├── 속성: 태스크, 담당도구, 우선순위, 예상시간, 실제시간, 상태
│   ├── 뷰: 칸반 보드 / 타임라인 / 번다운 차트
│   └── 관계: → 태스크 로그 DB
│
├── 📊 미해결 이슈 DB
│   ├── 속성: 이슈, 심각도, 발견도구, 관련코드, 상태, 해결방안
│   └── 뷰: 열린 이슈 / 기술부채 / 블로커
│
└── 📄 PROJECT_STATUS.md (자동 생성)
    ← Notion Agent가 위 DB들에서 요약 생성
    ← GitHub .ai/memory/mid-term/에 동기화
```

**Notion을 중기 메모리 허브로 쓰는 이유**: 이미 Claude Desktop에서 Notion MCP가 연결되어 있기 때문입니다. Claude Desktop에서 "이번 주 완료된 작업 목록 보여줘"라고 하면 Notion DB를 직접 쿼리합니다. 또한 Notion의 Custom Agents가 DB 갱신을 자동화할 수 있어서, 사람이 일일이 기록하지 않아도 됩니다.

### 2.2 GitHub Issues + Projects — "코드 연결 작업 추적"

코딩 관련 중기 메모리는 GitHub에서 코드와 함께 관리합니다. Issue에 작업 내용을 기록하고, PR에 연결하면, "이 코드가 왜 이렇게 바뀌었는지"가 코드 히스토리와 자연스럽게 엮입니다.

```
GitHub Project Board: AI Agent Development
│
├── Issue #42: "Model Router 구현"
│   ├── 라벨: feature, model-bridge
│   ├── 연결 PR: #43 (Claude Code로 구현)
│   ├── 코드 리뷰: Codex CLI로 수행
│   └── 상태: Done
│
├── Issue #44: "Notion MCP 메모리 동기화"
│   ├── 라벨: infrastructure, memory
│   ├── 연결 PR: (진행 중)
│   └── 상태: In Progress
│
└── Discussion: "A2A 프로토콜 도입 검토"
    └── 상태: Backlog
```

### 2.3 Google Drive — "공유 문서·산출물 보관"

코드가 아닌 산출물(발표 자료, 보고서, 스프레드시트)은 Google Drive에 보관합니다. Gemini와 Claude Desktop 모두 Google Workspace 연동을 지원하므로, AI 도구에서 직접 접근이 가능합니다.

```
Google Drive: AI-Agent-Project/
│
├── 📁 Presentations/    ← 아키텍처 발표 자료
├── 📁 Reports/          ← 월간 분석 보고서
├── 📁 Spreadsheets/     ← 비용 분석, 성능 벤치마크

### 2.4 중기→장기 승격 프로세스

중기 메모리에서 반복적으로 참조되는 패턴이 발견되면, 장기 메모리로 **승격**합니다.

```
승격 판단 기준:
  • 3회 이상 서로 다른 작업에서 참조된 패턴
  • ADR로 확정된 의사결정
  • 검증이 완료된 아키텍처 변경

승격 프로세스:
  1. Notion 태스크 로그에서 반복 패턴 식별
  2. .ai/memory/long-term/ 해당 문서에 추가
  3. GitHub commit: "promote: [패턴명] from mid-term to long-term"
  4. Notion ADR DB에 기록
  5. Obsidian 지식 그래프에 링크 추가
```

## 3. 단기 메모리 (Short-Term Memory): 도구별 네이티브 관리

### 7.1 미세조정 시나리오별 호환성 체크

아키텍처의 핵심 약속은 "어떤 변경이든 Core를 건드리지 않는다"입니다. 아래 시나리오들로 이 약속이 지켜지는지 검증합니다.

```
┌──────────────────────────────────────────────────────────────────────────┐
│  시나리오                      │ 변경 범위        │ Core 영향 │ 판정     │
├───────────────────────────────┼─────────────────┼──────────┼─────────┤
│ Notion을 다른 도구로 교체       │ 어댑터 1개 교체   │ 0줄      │ ✅ 호환  │

### 7.2 호환성이 보장되는 구조적 이유

이 아키텍처가 미세조정에 강한 근본적 이유는 세 가지입니다.

첫째, **마크다운이 범용 인터페이스**입니다. `.ai/` 디렉토리의 모든 파일이 마크다운(`.md`)이므로 어떤 AI 도구든 읽을 수 있습니다. 특정 도구의 독점 형식(`.notion`, `.obsidian` 등)에 의존하지 않습니다. Notion이 사라져도, Obsidian이 사라져도, 마크다운 파일은 그대로 읽힙니다.

둘째, **Git이 버전 관리 백본**입니다. 모든 변경은 Git 히스토리에 기록되므로, 어떤 미세조정이든 되돌릴 수 있습니다. "이 프롬프트 변경이 효과가 없었다" → `git revert`로 즉시 복원합니다.

셋째, **각 도구의 전용 파일이 간접 참조**를 합니다. CLAUDE.md, AGENTS.md, AGENT.md, GEMINI.md는 모두 `.ai/`를 "참조"할 뿐, 직접 내용을 담지 않습니다. 장기 메모리의 내용이 바뀌면 `.ai/` 파일만 갱신하면 되고, 도구별 파일은 건드릴 필요가 없습니다.

```
예시: CLAUDE.md의 구조

# Claude Code 프로젝트 지시

## 아키텍처 원칙
이 프로젝트의 아키텍처 원칙은 `.ai/memory/long-term/ARCHITECTURE.md`를 참조하라.

## 코딩 컨벤션
코딩 규칙은 `.ai/memory/long-term/CONVENTIONS.md`를 따르라.

## 현재 작업 상태
현재 프로젝트 상태는 `.ai/memory/mid-term/PROJECT_STATUS.md`를 확인하라.

## 이전 도구 인수인계
`.ai/memory/handoff/HANDOFF.md`가 있으면 먼저 읽고 이어서 작업하라.

---

↑ 이 파일은 "포인터"만 담고 있습니다.
  내용이 바뀌어도 이 파일은 수정 불필요.
  새 도구가 추가되어도 이 파일은 영향 없음.
```
