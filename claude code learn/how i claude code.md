먼저 제 소개를 한번 드릴게요.

## 라이브 목적

이 라이브의 목적을 좀 말씀드리자면, 일단 제가 어떻게 Claude Code를 쓰고 있는지를 좀 기초적인 수준에서 공유드리는 게 목적이에요. Claude Code 사용법 이런 걸 얘기하기보다는 "이렇게 쓰니까 더 좋더라" 같은 것들을 얘기하는 자리가 될 거 같고요.

두 번째 목적은 오랜만에 좀 소통하는 거. 그리고 이 라이브에 찾아와 주신 분들이 궁금해하시거나 좀 어려운 부분이 있을 거 아니에요. 그런 부분 좀 듣고 조언드리고 그런 걸 해보고 싶어서 했고요.

마지막으로는 제가 이렇게 제 방식을 공유드리면 누군가는 "어, 근데 그거 아닌데요. 이렇게 하는 게 더 좋던데요. 잘못됐는데요." 이렇게 말해줄 수도 있으니까요.

제가 하는 방식이 무조건 100% 정답이다 이렇게 생각하진 않습니다. 저도 맨날 조금씩 생각이 바뀌고 조금씩 하는 방식을 개선해 나가고 있어요. 제가 하고 있는 이 시행착오들을 공유드린다고 봐주시면 되겠고요. 딱히 자랑하려는 목적도 아닙니다.

**Claude Code 문서**는 말할 것도 없고요. Claude Code 문서 보면 생각지 못한 옵션들이 막 있을 때가 있어요. 그래서 좋고요.

그리고 되게 유명한 채널이죠, 유튜브 **AI Engineer**라고 있는데 이것도 되게 좋습니다.

## Claude Code를 쓰는 이유

먼저 Claude Code를 쓰는 이유부터 말씀을 드리고 싶어요.

일단 저는 Cursor 이제 안 씁니다. 아예 안 쓰고 있고 사실 안 쓴 지 좀 됐어요. 그리고 Claude Code를 완전 메인으로 쓰고 Codex, Gemini CLI 이 정도 약간 섞어서 쓰고 있는데 그 이유를 소개해드리자면:

**3순위: 토큰 제공량이 되게 많다**
200달러짜리 요금제 쓰시면 아마 절대 다 못 쓰실 거예요. 막 엄청 작정하고 쓰는 거 아닌 이상 엄청 많고요.

**2순위: Claude 모델 성능이 되게 좋습니다**
이 성능이 좋다는 말이 어떤 의미냐면, 제가 무언가 요구 사항이나 문서를 줬을 때 그걸 정확하게 구현하는 능력을 전 성능이라고 해요. 그 성능이 되게 좋습니다.

바이브 코딩에서 성능이라는 단어가 되게 여러 가지 의미로 쓰여요. 막 대충만 지시해도 잘 창작해내는 걸 성능이 좋다 이렇게 보시는 분들도 있는데 저는 그렇지 않고요. 저는 제가 어떤 지시를 했을 때 좀 틀리지 않고 누락하지 않는, 뭔가 그런 거를 성능이라고 봅니다.

**1순위: 에이전트 최적화 기능이 되게 많다**
서브 에이전트, 스킬, MCP, CLI 뭐 이런 여러 가지 좀 다른 에이전트 도구들에서 볼 수 없는 기능들이 많이 지원이 되는데요. 제가 보기에는 Anthropic에서 Claude Code를 엄청 많이 쓰는 거 같아요, 내부적으로. 그래서 막 쓰면서 자기들이 느낀 불편함을 조금씩 개선하는 느낌이거든요. 그래서 기능들이 되게 좋아서 저는 지금 Claude Code를 쓸 수밖에 없고요.

## Claude Code 추천 이유

저는 이 라이브를 보는 여러분들도 Claude Code를 쓰는 게 최선이라고 생각해요. 웬만하면요.

"나는 한 Lovable 정도로, 너무 어려워서 Lovable만큼 쉬운 거밖에 못 쓰겠어요" 하는 분들은 Lovable을 쓰셔도 되는데, 그게 아니라면 그냥 Claude Code 쓰시는 걸 추천드립니다. 왜냐면 단점이 없어요.

터미널이 만약에 불편하다 하면 익스텐션 되게 잘 나와 있거든요. 이거 그냥 쓰면 되고요.

Cursor의 비주얼 에디터 기능 있잖아요. 그것도 **React Scan**이라는 라이브러리가 있거든요. 이걸 쓰면 그냥 이렇게 선택할 수 있어요. 이걸 설치하면 내가 개발 환경에서 어떤 요소들을 이렇게 선택해서 여기에 그 선택자가 카피된 거거든요 지금. 그리고 이 카피된 거를 프롬프트에 붙여넣어서 "이거 어떻게 고쳐줘" 이렇게 얘기하면 돼요. 이런 기능 지원도 요런 걸로 대체해볼 수 있고요.

Windsurf 브라우저 자동화 기능도 되게 신기하고 참신한 기능이기는 한데 막 필수적이진 않아요 사실. LLM한테 브라우저 테스트를 맡긴다는 거 자체가 되게 웬만한 상황에선 비효율적이거든요. 스크립트로 짜놓고 E2E 테스트로 돌리면 훨씬 빠르고 정확하게 돼요.

하나의 도구에서 여러 가지 모델을 한 번에 쓰고 싶다 이러면 사실 Claude Code를 못 쓰기는 하죠. 근데 이것만 아니면 웬만한 분들은 다 그냥 Claude Code 쓰시는 게 최고입니다.

## 바이브 코딩을 잘하려면

이제부터 좀 바이브 코딩을 잘하려면 어떻게 해야 될까에 대해서 좀 얘기를 하고 싶어요.

저는 바이브 코딩을 잘한다는 게 그냥 **컨텍스트를 잘 관리하는 거**랑 똑같다고 생각해요.

왜냐하면 컨텍스트를 관리할 필요 없는 작업은 이미 AI가 엄청 잘해요. 막 에러 메시지 붙여놓고 고쳐달라고 한다던가 그런 거는 다 그냥 프롬프트 한번 하면 웬만하면 그냥 작업 다 잘 되거든요. 요새 AI 모델 성능이 좋아져서 막 그런 데 있어서 엄청난 프롬프트 기법이라던가 그런 게 있진 않아요.

뭐 개발에 대해서 많이 공부하면 좋을 수는 있겠죠. 근데 그거는 그냥 AI 모델이 할 생각을 내가 대신 해주는 거잖아요. 그러니까 사실 그게 바이브 코딩을 잘하는 거라고 보긴 좀 어렵죠.

제가 말씀드리고 싶은 거는 바이브 코딩을 한다는 거 자체는 사실 딱히 배울 건 없어요. 그냥 요새는 적당히 명령하면 AI 모델들이 다 알아서 잘 해주는 시대인데, 못하는 작업이 있죠.

못하는 작업이 뭐냐면 **컨텍스트가 모자라거나 어쨌든 컨텍스트 관리가 필요한 작업**들은 이제 좀 엔지니어의 터치가 필요한 영역인 건데요.

정리하자면 바이브 코딩을 잘한다는 거는 지금 **컨텍스트를 잘 관리한다**는 말이랑 거의 동의어입니다.

## 컨텍스트 관리가 필요한 순간

컨텍스트 관리가 필요한 순간이 대표적으로 두 가지가 있어요.

**첫 번째는 컨텍스트 사이즈 자체가 모자란 경우**
예를 들면 이 서비스에 있는 보안 취약점을 전부 찾아야 된다던가, 아니면 신규 아키텍처 구조로 리팩토링을 전부 적용해야 된다던가 하면 그냥 모자라고요.

**두 번째는 안 모자라도 잘 못할 때**
지시 사항을 길게 입력했을 때 누락되는 문제가 있어요. 이 누락됐다는 게 해야 하는 작업을 안 하거나 아니면 대충 하는 걸 의미해요.

이렇게 두 가지 문제가 발생할 수 있는데 이거를 적절히 조치해주는 게 그냥 바이브 코딩이에요. 제가 보기엔 그렇습니다.

이런 컨텍스트 문제가 발생하는 원인은 그냥 **LLM이 생각할 거리가 너무 많기** 때문이에요. 한 번에 뭔가 고민이라던가 작업하는 호흡 자체가 너무 길어서 막 한 호흡 챌린지로 막 한 10분 이렇게 할 수 없잖아요. 숨이 딸려서. 그런 느낌이라고 봐주시면 됩니다.

## Anthropic의 컨텍스트 최적화 도구들

우리는 이제 이 컨텍스트를 잘 관리해줄 필요가 있는데, 컨텍스트를 어떻게 하면 잘 관리할 것이냐. 이게 제가 생각해낸 건 아니고요. Anthropic에서 컨텍스트를 잘 관리하기 위한 여러 가지 도구나 기능들을 내놓았어요 이미.

그것들로부터 "아, 이 기능이 나온 거는 이렇게 컨텍스트를 최적화하기 위함이구나"라고 역으로 추론을 한번 해보겠습니다.

### 1. 플랜 모드 (Plan Mode)

플랜 모드가 뭐냐면 Claude Code에서 쓸 수 있는 기능인데, 이걸 하면 **탐색하는 단계**랑 **계획하는 단계** 그리고 **구현하는 단계**를 다 각각 나눠놔요.

채팅에도 Cursor에서 쓰던 'Step by Step' 룰을 질문 주신 분이 있는데, 이 Step by Step 룰을 되게 모드로서 완전 강제한 게 플랜 모드라고 보면 돼요.

플랜 모드의 특징이 뭐냐면 이 탐색 단계랑 설계 단계, 구현 단계 각각의 단계가 명확하게 컨텍스트가 나누어져 있고, 그 결과를 마크다운으로 소통한다는 거예요.

설계 단계를 끝마치고 나서 설계 문서를 쓰거든요. 그게 마크다운으로 저장되어 있어서 구현 단계에서 그걸 참고해서 작업을 하는데, 말씀드리고 싶은 게 **작업을 적절한 단계로 나누고 중간 문서를 만들었다**는 거고요.

### 2. MCP CLI

Anthropic 블로그에 올라왔던 건데, MCP를 그냥 호출하면 MCP를 호출하기 위한 데이터랑 MCP가 호출된 이후의 데이터가 전부 다 컨텍스트에 남거든요.

그게 좀 불필요하다 이거죠. 예를 들면 제가 가르치는 학생 데이터베이스가 있다고 할게요. 그리고 그 학생 중에 점수 1등을 뽑고 싶은 거예요. 그러면 MCP를 그냥 쓰면 학생 데이터를 전부 다 컨텍스트 안에 불러온 다음에 그 불러온 데이터 중에서 1등을 찾을 수가 있거든요 LLM이.

근데 그러면 제가 궁금한 건 그냥 1등이 누군지인데 괜히 학생 전체 데이터가 불러와진 거잖아요. 그걸 방지하기 위해서 중간 단계에서 이 데이터를 불러오고 1등을 찾아내는 거는 코드로 처리하고 **결과만 이렇게 전달하는 방식**이거든요 MCP CLI가.

아무튼 이렇게 **불필요한 정보 걷어내는** 거고요.

### 3. 스킬 (Skills)

스킬은 많이 아실 것 같기는 한데, 이거는 에이전트한테 필요한 지식 같은 거를 처음부터 다 때려넣는 게 아니라 **필요할 때마다 불러오는** 거예요. 결론적으로 불필요한 정보가 컨텍스트 내부를 점유하고 있는 거를 막겠다 이거죠.

### 4. MCP IDE Get Diagnostics

## 컨텍스트 최적화 정리

정리하자면 컨텍스트를 최적화하는 좋은 방법은 이렇게 세 가지가 있는데:

1. **내가 하는 작업의 단계들을 나누고 각 단계들이 마크다운으로 소통하게 만드는 것**
2. **컨텍스트에 포함되는 불필요한 정보들을 최대한 걷어내는 것** (필요한 것만 불러오게 만들거나 중간 데이터가 남지 않게 하는 것)
3. **에이전트에게 당신의 작업을 자체 검증할 수 있는 도구를 쥐어주는 것**

일단 이 기능들을 그냥 쓰기만 해도 요런 최적화가 그냥 적용되는 거긴 해요. 그래서 오늘 라이브에서는 이 기능들을 일단 한 번씩 제가 쓰고 있는 방식으로 보여드리고, 그리고 두 번째로 이 철학을 제가 좀 반영해서 만들어낸 저만의 방식들을 또 소개해드릴게요.

## 대량 컴포넌트 생성 워크플로우

이거를 어떻게 했는지에 대해서 좀 말씀을 드리고 싶어요. 에이전트 사용해서 했거든요.

### 1단계: 이미지 URL 추출

사이트별로 크롤링하기도 했고요. 아니면 어떤 디자인 모음집 사이트에서 통째로 긁어오기도 했거든요.

디자인 모음집을 긁어온 방법을 한번 보여드릴게요. SaaS Landing Pages 뭐 이런 서비스들이 있잖아요. 디자인 모여있는 서비스. 근데 이런 서비스는 좀 크롤링하기가 애매한 게 이미지를 보고 구현을 해야 되는데, 사실 이 디자인이 예쁜 이유는 그냥 이 이미지가 다 한 거거든요. 그래서 레퍼런스로서 좀 의미가 약하고, 저는 **Unsection**이라는 곳을 많이 참고를 했었어요.

여기에서 이 목록을 가져오는 거예요. 이 부분을 Inspect 해서 Copy Element를 하잖아요. 그럼 이 부분에 대한 HTML이 복사가 돼요.

이 HTML로부터 이 이미지들을 전부 뽑아낼 거예요. 근데 뽑아낼 때 AI한테 시킬 건데, AI한테 그냥 시키면 컨텍스트 사이즈가 너무 커요.

그래서 저는 **htmlslim.com**을 쓰거든요. 참고로 제가 만들었습니다. 여기에 HTML을 넣으면 39,000자죠 지금. 근데 이렇게 줄이면 18,000자로 줄어요. 어떻게 이렇게 줄어냐면 불필요한 속성들을 다 없애는 거예요.

이렇게 줄인 다음에 AI Studio 같은 데 찾아가는 거죠. 찾아가서 좋은 모델 Gemini 2.5 Pro 여기에서 이렇게 뽑고:

> "아래 HTML에 대해서 카드들의 정보를 썸네일 정보를 추출해라. 여기서 Name, URL, Image URL 형식으로 한 줄에 하나씩 텍스트로 추출하면 된다."

이렇게 하면 얘가 뽑아줘요.

### 2단계: 이미지 다운로드

이미지 추출은 npm 명령어로 호출하고요. 스크립트를 만들어놨어요. `dataString`이라는 거를 만들어놓고 여기에 붙여넣으면 이미지들이 다운로드가 되거든요.

### 3단계: 체크리스트 생성

체크리스트를 만드는 건 LLM한테 시키고 있는데, 체크리스트 만드는 거는 코드로 만들어놓으면 체크리스트의 스펙이 바뀌었을 때 코드를 수정해야 되잖아요. 근데 체크리스트 스펙은 제 생각에는 좀 더 바뀌기 쉬운 존재거든요. 이미지를 다운로드하는 것보다 체크리스트를 만드는 게 좀 더 유지보수할 가능성이 높은 로직인데, 이렇게 좀 바뀔만한 거는 저는 **프롬프트로** 해요. 왜냐하면 프롬프트가 고치기 더 쉬우니까요.

체크리스트가 어떤 거냐면 각각의 이미지들에 대해서 작업을 했는지 안 했는지를 관리하기 위한 문서거든요. 근데 이게 지금 이미지 자체가 많으니까 이렇게 줄 수가 많아져요. 500줄 이렇거든요.

그럼 이 500줄짜리 문서를 AI 에이전트한테 그냥 쓰라고 하면 컨텍스트를 너무 먹고 너무 오래 걸려요. 그래서 그렇게 하기 싫으니까 "나는 이 **스크립트 작성 후 실행하라**"고 했거든요.

이게 뭔 소리냐면 이거를 네가 한 땀 한 땀 쓰지 말고, 이 파일을 생성하는 코드를 작성한 다음에 그걸 그냥 실행하라는 거예요. 실행 성공하면 스크립트 파일은 제거해라.

이렇게 뭔가 좀 **규칙적인 작업을 시킬 때는 그냥 시키지 말고 그 작업을 하기 위한 스크립트를 작성한 다음에 실행하라**고 하면 좋아요. 그러면 좀 컨텍스트도 아껴지고 정확도도 높아지고 속도도 빠르겠죠.

### 4단계: 병렬 컴포넌트 구현

하나하나 컴포넌트를 구현할 차례거든요. 지금 48개 있었는데 48개를 이렇게 하면 한 번에 할 수 있습니다.

어떻게 되는 거냐면요, 메인 에이전트가 사실 작업을 딱히 안 해요. 메인 에이전트는 **관리자만** 하고 이 서브 에이전트들이 구현을 다 해요.

메인 에이전트가 일단 체크리스트에서 아직 안 한 것들 파악하고, 병렬로 호출해가지고 구현 작업은 얘네한테 다 맡기는데요.

저는 20개씩 하는 이유는 더 많이 하면 좀 과부하가 걸려요. 그리고 한 50개 한 번에 요청해도 50개를 병렬로 실행하기는 하는데 얘가 그냥 앞에 열 개부터 처리를 하거든요. 한 열 개 조금 넘게 하는 거 같은데. 그래서 저는 20개씩만 하고 그다음 거 하고 이렇게 하라고 합니다.

또 이렇게 나눠서 하는 게 좋은 게, 나눠서 시키고 그 단위가 끝나면 완료 체크하라고 했거든요. 중간중간 완료 체크를 해야 나중에 혹시나 작업이 막 취소되더라도 좀 이어서 할 수 있잖아요.

## 서브 에이전트 최적화

이미지 컴포넌트 에이전트를 한번 볼게요. 서브 에이전트가 지금 어떻게 돼있냐면 이미지를 전달받아서 컴포넌트로 구현하는 거고요.

여기에는 작업에 대해서 어떻게 해야 되는지가 그냥 다 명시가 되어있어요. 프롬프트들이 되게 자세히 적혀있는데 이렇게 적힌 이유는 **이렇게 안 적으면 정확하게 안 해서** 그래요.

저도 처음부터 이렇게 만들지는 않았는데 해보면 뭔가 작업을 잘 못하거든요. 그래서 그런 부분들을 보완하려고 막 이렇게 프롬프트를 많이 쓴 겁니다.

그리고 또 이 서브 에이전트에 **적절한 MCP를 쥐어주는 것**도 되게 좋아요. 그래서 그런 적절한 MCP가 없으면 제가 직접 만들었거든요.

프롬프트를 보면 "이미지에 포함된 주요 요소들의 정확한 컬러를 가져오세요. Sharp MCP를 사용해서 정확히 추출하세요"라는 문구가 써있어요. 이 Sharp MCP가 제가 구현한 거예요. 이미지의 특정 좌표의 컬러를 추출하는 기능을 Sharp MCP에 제가 구현해놨거든요. 이렇게 좀 이미지 투 컴포넌트 에이전트에 필요할만한 도구들을 막 쥐어준 거고요.

여기에서 서브 에이전트가 할 작업을 그냥 프롬프트로 하는 게 아니라 **스크립트 파일을 만들어놓고 코드를 실행하게** 해요.

이렇게 하면 좋은 점이 뭐냐면 서브 에이전트가 작업하다가 뭐 하나씩 누락할 수도 있잖아요. 그건 자연스러운 일인데, 이렇게 코드로 정의를 해놓으면 이 중에 하나라도 누락하면 이 코드가 그냥 실패해요. 실패하면서 에이전트에 에러 메시지를 줄 수 있잖아요. 그럼 얘가 누락했던 걸 보완해서 다시 호출하거든요. **정확도가 중요한 작업에서는 이렇게 코드를 만들면 좀 해결이 됩니다.**

## 스크립트화 패턴

많은 분들이 이렇게 잘 안 하시는데 이렇게 하시는 게 정확도 측면에서 훨씬 좋습니다.

예를 들면 다른 프로젝트 한번 열어보면 여기에 React 코드인데 이런 코드를 많이 쓰실 거거든요. 이런 좀 규칙적인 코드 있잖아요. 전부 다 `use`로 시작하고 이런 것들을 코드를 통째로 LLM이 쓰게 하지 말고 **`createHook`이라는 스크립트를 짜는** 거예요.

이 파일을 참조시켜놓고:

> "위 파일을 통해서 이 프로젝트에서 훅을 작성하는 규칙을 파악하고, 훅 코드를 작성하는 스크립트 파일을 생성하고 싶다. 이 스크립트는 새 파일을 생성할 수도 있고 기존 파일에 새로운 훅을 추가할 수도 있다. 적절한 아규먼트를 가져야 하며, 아규먼트 값 중 오류가 있으면 적절한 에러 메시지를 반환해야 한다. 이 스크립트의 스펙을 자세하게 계획하라."

이러고 플랜 모드 쓰는 거죠.

이런 식으로 좀 어떤 프로젝트에 대해서 규칙적으로 작성되는 코드 있잖아요. 그러면 그 코드를 그냥 에이전트 지침으로 때려박지 말고 그냥 그렇게 **규칙적으로 이 코드를 생성해내는 스크립트를 쓰는** 거예요.

이렇게 하는 편이 규칙 관리도 잘 되고 속도 빠르고 컨텍스트 관리도 되고 그렇습니다.

## 후처리 에이전트

컴포넌트들 추가됐죠. 컴포넌트 추가하고 나서 후처리도 해야 되거든요. 후처리해야 되는데 그것도 서브 에이전트로 따로 따놨어요.

이 서브 에이전트를 골뱅이(@) 기호로 참조해서 명시적으로 호출할 수 있거든요. 이렇게 `@build` 하니까 이렇게 뜨는데 딱 잡아놓고:

> "@build를 사용해서 점검 및 후처리하고, 전부 잘 완료되면 변경된 모든 파일을 적절히 커밋해라."

이렇게 해놓고 그냥 또 기다리면 되는 거죠.

이 에이전트는 뭐하는 에이전트냐면 지금 코드에 있는 각종 오류들을 전부 확인해서 조치하고, 메타데이터가 잘못된 거 확인하고 만약에 잘못된 게 있으면 적절히 고치고요. 빌드도 하고, 스크린샷도 다 찍고, 컴포넌트들에 대해서 하나하나 스크린샷을 찍어요.

이거를 에이전트로 만든 이유는 여기 중간중간에 좀 검증하고 잘못되면 고쳐야 되는 로직이 있잖아요. 이걸 수행시키기 위해서 에이전트로 만든 거고요.

이 에이전트의 특징이 얘는 원래 하이쿠(Haiku) 썼었는데 제가 빼놨네요. 이렇게 좀 단순하게 빌드 같은 작업하는 에이전트는 **모델을 좀 낮은 걸 써도** 괜찮고요.

## 서브 에이전트 vs 스킬 차이점

**서브 에이전트랑 스킬은 아예 개념 자체가 완전 달라요.**

### 서브 에이전트
서브 에이전트는 쉽게 말하면 **메인 에이전트가 다른 하위 에이전트한테 외주 작업을 맡길 수 있는** 거예요. 여기서 포인트가 '외주 작업'이라는 거거든요. 그래서 컨텍스트를 완전히 공유하지 않아도 괜찮은 걸 시키는 게 좋아요 보통.

주 대화와 분리된 자체 컨텍스트 윈도우를 사용합니다.

### 스킬
스킬은 쉽게 말하면 **프롬프트를 특정 작업에만 필요한 프롬프트를 필요할 때만 불러오도록 만드는** 느낌이에요.

### 비교 정리

서브 에이전트는 **메인 에이전트와 협업하는 하위 에이전트**를 만드는 기능인 거고요. '하위 에이전트'가 포인트입니다. 특정 작업을 **하청**시킨다, 하청 준다 이런 거고요. 원청에서 엄청 중요한 작업은 하청 안 주잖아요. 그냥 막 시키면 잘 해줄 수 있는 걸 하청 주잖아요. 그게 좀 맥락이 분리돼서 그러는 건데 현실 세계에서도 그렇죠.

스킬은 이거랑 다르게 **메인 에이전트의 특정 작업에 대한 지침을 필요할 때만 불러오는** 기능입니다. 여기서 포인트는 '필요할 때만'입니다.

### 그림으로 설명

디자인을 서브 에이전트한테 시키는 거랑 스킬로 관리하는 거랑 다르거든요.

디자인을 담당하는 서브 에이전트를 만들면 메인 에이전트는 디자인과 관련된 내용을 **아예 몰라요**. 그리고 그냥 그 서브 에이전트한테 "디자인 이쁘게 만들어줘" 이렇게 시키는 거거든요.

근데 스킬을 쓰면 메인 에이전트에 '디자인 잘하는 법'을 불러오는 거예요. 그리고 **메인 에이전트가 디자인을 하는** 거죠.

딱 봐도 스킬 경우의 수가 얘가 지금 벌써 막 넘치려고 하잖아요. 그러니까 이거는 이 정보가 메인 대화 세션에 불러와진 거고요, 서브 에이전트는 디자인 구현은 얘한테 하청 준 거다.

## 스킬 vs MCP 선택 기준

서브 에이전트를 쓸 때랑 스킬을 쓸 때를 저도 솔직히 지금 딱 정리하라고 하면 못 할 거 같은데, 근데 저는 사실 **스킬은 거의 안 써요**.

왜냐하면 어쨌든 이 컨텍스트가 여기에 더해지는 거잖아요. 이거 자체가 저는 좀 불편하거든요. 그래서 잘 안 씁니다.

스킬이 발전하면 토큰을 무조건 더 아낄 거라 효율적일 것 같네요라고 하셨는데, 그렇지도 않아요 사실. 스킬이랑 MCP랑 엄청 크게 다르진 않아요 사실.

스킬이 궁극적 형태 같진 않아요 사실. Cursor 룰에 옛날부터 있던 기능이거든요 스킬이. 근데 그냥 이름이 스킬이라고 붙은 거예요. Cursor 룰에 'Apply Intelligent' 있죠. 이게 그냥 스킬이에요.

저는 훨씬 나은 형태가 나오지 않을까 싶어요.

## 내가 만든 커스텀 MCP

### 1. Git Batcher MCP

Git 저장소를 배치해주는 MCP예요. 제가 개발할 때 어떤 오픈소스 저장소를 계속 참조하면서 개발하고 싶을 때가 있거든요. 근데 그 저장소의 코드를 계속 가져와서 막 넣어주자니 너무 번거러운 거예요.

"이 저장소에 이 파일을 참고해서 구현해줘" 이렇게 하고 싶은데, 그래서 그걸 하기 위해서 만든 MCP예요.

`fetchFile`이라는 툴이 있거든요. 이걸 쓰면 뭐 제가 만약에 facebook/react라는 레포지터리를 연동해뒀다 이러면, 파일 경로만 입력하면 이 저장소의 파일 내용을 불러올 수 있어요.

스킬로 안 만든 이유는 이게 저는 많은 프로젝트에서 이 기능을 쓰고 싶었어요. 근데 제가 이걸 스킬로 만들면 각각의 프로젝트에 스킬을 다운로드 받아서 설치해야 되고, 제가 이걸 유지보수 할 때마다 모든 프로젝트에 대해서 업데이트 해야 되잖아요. 그게 너무 귀찮아요. 그래서 MCP로 만들었고요.

이 MCP가 용량을 많이 안 먹어요. 1.6%밖에 안 먹어요. 별로 안 먹어서, MCP를 엄청 크게 만들어버리면 좀 오버헤드가 될 수 있는데 잘 만들면 그냥 그렇게 안 됩니다.

### 2. Nanobana API MCP

말 그대로 Nanobana API로 호출해주는 MCP예요. 이것도 만든 이유 동일하죠. 여러 개의 프로젝트에서 이 기능을 쓰고 싶은데 스킬로 만들면 일괄 업데이트를 못 하니까 MCP로 만들었고요.

### 3. Sharp MCP

이미지 프로세싱 하는 MCP예요. 이미지 배경 제거하고, 이미지 크기를 막 불러온다던가, 이미지에서 색상을 추출한다던가, 배경 제거한다던가 이런 기능들을 다 갖고 있어요.

다 쓰실 수 있습니다. 그냥 쓰시면 돼요.

## 엔터프라이즈 레벨 파이프라인

이제 좀 고급 코스예요. 어디 컨퍼런스에서 발표했던 자료인데 이것도 좀 흥미로워하실 만한 분들이 있을 것 같아서 준비해봤어요.

지금까지는 제가 작은 프로젝트에서 이걸 어떻게 쓰고 있는지를 보여드린 건데, 이것과 좀 개념은 동일한데 **엔터프라이즈 레벨에서는 어떻게 할까**를 말씀드리는 거거든요.

"나는 바이브 코딩으로 막 수익화를 해보고 싶어" 이런 분들한테는 별로 적용 안 되는 내용이에요.

## 바이브 코딩의 딜레마

바이브 코딩 자체는 되게 쉬워요 사실. 프롬프트 한번 입력하면 거의 다 되죠.

근데 개발자 입장에서 생각해봤을 때 좀 아쉬운 부분이 여전히 남아있어요. 뭐가 아쉽냐면 AI를 사용함으로써 내가 얼마나 작업을 더 많이 할 수 있게 되었나, 얼마나 빨라졌나를 솔직히 좀 객관적으로 되돌아보면 **그렇게 드라마틱하진 않아요** 사실.

바이브 코딩을 딱 했을 때 내가 2인분을 하는가, 막 AI가 없을 때 개발자 세 명이 붙어서 해야 할 일을 내가 하고 있는가라고 하면 솔직히 아니에요.

아닌데 그 이유가 뭘까를 생각해보니까 개발자가 일하는 시간 중에 **구현을 하고 있는 시간이 그렇게 길지 않아요** 사실.

원래 막 그런 말도 있거든요. 개발자가 막 키보드를 막 치고 있는 것보다 그냥 모니터 뚫어져라 쳐다보면서 인상 찌푸리고 있는 게 사실 더 일을 열심히 하고 있는 상태다 이런 말도 있는데, 의사소통하고 코드 설계하고 막 그런 작업이 원래 더 어렵고 더 오래 걸리는 일이라는 거죠.

### 바이브 코딩의 딜레마

- **간단한 작업**: 프롬프트 한 번 입력하면 되지만, 간단한 작업을 대신해주는 건 **생산성 증가 효과가 적음**
- **복잡한 작업**: 생산성 증가 효과는 높은데 AI 코드를 어차피 검토해야 되고, 설계도 사실상 잘 위임하기가 쉽지 않음

좀 미미하다. 사실상 키보드 타이핑밖에 위임을 못 한다.

## 개발자 작업 단계 분석

개발자의 작업이 요런 단계로 구분될 수가 있거든요:

1. **Clarify (요구사항 구체화)**: PM이든 디자이너든 구현하기 위해서 뭔가를 주면 여기서 좀 더 구체화를 해야 돼요. 디자이너가 뭔가를 줄 때 모든 상태를 고려해서 주는 경우가 별로 없어요.
2. **Design (설계)**
3. **Implement (구현)**
4. **Verify (검증)**: 구현한 거를 빌드, 테스트 깨지는지 이런 거 점검
5. **Review (리뷰)**: 다 통과하면 동료랑 같이 리뷰하면서 최종 점검

이 중에서 **앞단계를 맡기기 어려운 이유**가 앞단계에서 뭔가 잘못되잖아요. 그럼 그게 뒷단계에 다 전파돼요. 그러면서 코드가 크게 망가져요.

앞단계에서 좀 사소한 실수가 있었어도 그렇다 보니까 이 앞단계를 자신있게 맡기가 어려운 거죠. 왜냐하면 그렇게 맡겼다가 조금만 잘못돼도 코드가 박살이 나니까. 그래서 쓸 수 없게 되니까.

그래서 많은 경우에 개발자분들이 **구현이랑 검증만 맡겨요** 보통. 자기가 요구사항 다 정해놓고 설계도 다 하고 그다음에 구현이랑 검증만 맡기는 거죠.

근데 아까 말씀드린 것처럼 사실 대부분의 작업은 이게 잘 돼있으면 이건 원래 쉬워요.

## 파이프라인화가 효과적인 작업

제가 컨설팅을 가면 이런 작업들을 AI 에이전트에 위임을 하는데요.

제가 바이브 코딩을 여러 가지 측면에서 활용을 많이 해봤었는데 한번 보면:

- 마이그레이션 (레거시 프로젝트를 새로운 기술 스택으로)
- 개발팀 생산 효율성 증가
- 제 SaaS를 만들 때
- 만들어진 코드를 문서화할 때
- 스펙 기반으로 어떤 걸 만들 때
- 기능 추가할 때

**가장 효과가 좋은 게 두 가지**였어요: **마이그레이션**이랑 **스펙 기반으로 개발할 때**

## 파이프라인 적용 사례 1: 레거시 마이그레이션

공장에서 쓰는 ERP였는데 되게 엄청 옛날 언어랑 옛날 기술 스택을 써서 구현된 거였어요. 이거를 Next.js로 옮기고 싶다고 하시더라고요.

엄청 큰 코드베이스를 옮겨야 됐어요. 기능도 되게 많았고요. ERP가 거의 진짜 웬만한 소프트웨어보다 훨씬 큽니다. 공장이 오래 운영됐을 테니까 그러면서 막 발생했던 모든 엣지 케이스가 이 코드베이스에 담겨있거든요. 진짜 복잡합니다.

### 파이프라인 구조

이거 하나하나가 서브 에이전트예요. 메인 대화 세션이 있고 여기서 프롬프트 이렇게 입력하면 서브 에이전트들이 순차적으로 호출되면서:

1. 스펙을 쓰고 → 사람이 검토
2. 탐색하고 컨벤션 탐색하고 보고서 작성 → 사람이 검토
3. 구현

이게 뭐 꽤 단순하게 좀 표현이 되어있는데 각각의 에이전트에 시스템 프롬프트도 잔뜩 적혀있고 또 필요한 MCP나 스크립트 같은 것도 다 작성해서 막 꽂아줬거든요. 그래서 사실 꽤 방대한 파이프라인입니다. 이거 만드는데 한참 걸려요.

### 파이프라인 특징

- 각 페이지(Specify, Research, Plan, Implement)의 **결과만 사람이 검토**
- 시작하기에 앞서서 제대로 이해한 게 맞는지 **한번 되묻게** 했어요
- 중요한 작업만 **Opus**가 하고 병렬로 하거나 구현은 전부 다 **Sonnet**
- 플랜을 애초에 좀 디테일하게 쓰니까 구현 단계에서는 오히려 지능보다 Sonnet이 토큰이 훨씬 싸잖아요. 비용 최적화 관점에서 Sonnet을 사용

### 결과

엄청 큰 코드베이스였는데 **일주일 만에 마이그레이션을 성공**했습니다.

물론 구현은 일주일 걸렸는데 **파이프라인 세팅하는 게 2주** 걸렸어요. 왜냐하면 이렇게 만들어놓고 진짜 최적화를 엄청 많이 해야 돼요. 막 스크립트 뭐 줬다가 막 MCP도 막 커스텀으로 만들어서 막 쥐어주고.

그래서 14일 동안 막 때려박아서 이걸 하고 여러 번 제가 이터레이션도 돌리고 괜찮아보이니까 이제 그쪽에 줘서 "쓰세요" 이렇게 해서 한 거고요.

7일 만에 그쪽 개발자분이 구현을 다 하셔서 배포 가능한 상태였는데, 마이그레이션 7일 만에 완료되기는 했지만 이게 완벽한 상태는 아니었어요. 그래서 배포해놓고 버그가 좀 있었거든요. 그거를 내부 구성원분들한테 좀 클로즈드 베타 느낌으로 배포해서 쓰면서 좀 안정화하는 기간을 거쳐야 됐어요. 14일 정도 거치셨고요.

이 기간 지난 후에는 완전히 안정화가 됐습니다. **이게 한 달 만에 됐어요.**

이게 말이 안 돼요. 개발자분들은 아실 텐데. 바이브 코딩 에이전트를 극한으로 쓰면 이렇게 할 수 있다 이런 거고요.

## 파이프라인 적용 사례 2: 스펙 기반 ERP 생성

공장을 위한 외주 개발사였는데, 세일즈 직군이 공장을 돌아다니면서 공장의 요구사항을 파악하는 거예요. 요구사항을 파악하고 그거를 정리해오면 개발자가 그 공장에 필요한 소프트웨어를 구현해주는 그런 회사였어요.

맨땅에서 하진 않고요. 템플릿이 있었습니다. 그래서 이 템플릿 기반으로 좀 스펙에 따른 초안을 뽑아내는 그런 걸 자동화하고 싶은 거였죠.

### 커스텀 MCP 필요성

스펙을 원래 파워포인트로 남기셨거든요. 근데 파워포인트는 AI한테 입력하기가 되게 난해해요. 데이터 포맷 자체가. 그래서 그거를 애초에 파워포인트를 쓰지 않으시도록 **프로세스 자체를 개선**해야 됐어요. 노션이랑 스프레드시트로 정상화를 했고요.

각 에이전트들이 뭐 예를 들면 회의록은 노션에 저장됐거든요. 그러면 이 노션 데이터를 불러올 때 **노션 MCP를 그냥 쓰시면 안 돼요**.

왜냐하면 그런 퍼블릭 MCP들은 너무 제공하는 툴도 많고 프롬프트도 너무 장황하게 써있고 그렇거든요. 그래서 그런 MCP들을 참고 삼아서 **커스텀 MCP를 만들어야** 돼요.

바이브 코더분들이 다 이렇게 해야 된다는 건 아닌데, 저처럼 파이프라인을 극한으로 최적화해서 엄청 대용량 작업을 시키겠다라고 희망하시는 분들은 그냥 무조건 이렇게 하셔야 돼요.

### 결과

**원샷으로 초기 구현이 가능한 파이프라인**을 만들었습니다.

개발자분들은 아쉽겠지만 50개의 기능을 갖고 있는 ERP를 원샷으로 만든다, 이거 말이 안 되거든요. 말이 안 되는데 말이 되게 만들 수가 있습니다. 극한으로 최적화를 하면 Claude Code를 쓰면 가능합니다.

물론 미친 듯이 해야 돼요.

## 파이프라인 적용 조건

이 세 가지는 **필수**예요. 하나만 빠져도 보통 파이프라인화가 안 돼요:

1. **Well-defined (잘 정의됨)**: 스펙이 어줍잖은 기획서 수준이 아니라 진짜 엄청 정확해야 함. 유비쿼터스 언어 쓰면서 코드 레벨로 그대로 옮길 수 있을 정도로 정확해야 됨
2. **Self-verifiable (자체 검증 가능)**: 에이전트가 스스로 검증할 수 있어야 함. 디자인 같은 거 있잖아요. 디자인은 에이전트가 검증하기 어렵거든요.
3. **Rule-based (규칙 기반)**: 규칙에 따라 구현하는 작업이 많이 있어야 됨

예를 들면 Self-verify가 안 된다 이러면 사람이 검증해야 되니까 너무 번거워서 파이프라인화가 안 됩니다.

## 바이브 코딩 vs 파이프라인

제가 소개해드린 파이프라인 기법이 사실 바이브 코딩보다 우월한 기법이냐, 그건 아니에요. **용도가 다른** 겁니다.

- **바이브 코딩**: 작업 주체가 개발자고 그냥 "이거 해줘 저거 해줘" 이렇게 요청. 잘 정의되어 있지 않은 작업이거나 창의적으로 수행할 때 적합
- **파이프라인**: 되게 규칙적이고 지루한 작업. 개발자분들은 공감하실 텐데 회사에서 뭔가 멋없는 일들 있거든요. 되게 지루한 지원 업무 하는 팀. 그런 지루한 작업들은 파이프라인화해서 시키면 되게 잘합니다.

**둘이 좀 상호 보완적**이라고 보시면 될 거 같아요.

내가 개발자로서 좀 고민을 많이 하고 되게 고도화하는 작업은 바이브 코딩으로 하시고, 규칙적인 그런 작업들, 지루한 것들은 에이전트한테 그냥 시켜버리세요.

Claude Code에 플랜 모드를 그냥 쓰시기만 해도 파이프라인화해서 하는 코딩을 좀 맛보기로 체험하실 수 있습니다. 꼭 플랜 모드를 한번 써보시길 추천드려요.

## 파이프라인 설계 가이드

### 파이프라인 설계 프로세스

1. 페이지별로 서브 에이전트를 다 하나씩 만들고
2. 그다음에 서브 에이전트를 극한으로 최적화 (도구 쥐어주고 프롬프트 최적화하고)
3. 막 서브 에이전트 네 개 만든 거 분해하고
4. 이걸 무한 반복

### Claude Code를 추천하는 이유

서브 에이전트 기능이 Claude Code에만 있어요 제가 알기론. 그래서 Claude Code를 쓸 수밖에 없고요.

### MCP vs 스킬 (팀 환경)

파이프라인 최적화 관점에서는 **MCP가 더 좋아요**.

스킬이랑 MCP랑 뭔가 비슷한 역할인데, 개인 입장에서는 스킬을 쓰는 것도 괜찮은데, 회사에서 공용으로 쓸 거라면 MCP는 **서버로 배포**할 수 있거든요. 이 서버를 재배포하면 이 MCP를 쓰고 있는 모두가 신기능을 바로 써요.

근데 스킬은 파일로 관리되다 보니까 모든 프로젝트에서 새로운 스킬을 다운받아야 돼요. 그래서 현실적으로 쓸 수가 없었습니다.

### 기타 필수 사항

- **레이어드 아키텍처**는 거의 무조건 꼭 지켜야 돼요
- **대규모 리팩토링** 같은 것도 다 시킬 수 있어요. 아까 말씀드린 세 개의 특성(Well-defined, Self-verifiable, Rule-based)만 준수하면 됩니다

## 커스텀 MCP 장점 상세

노션 MCP 대신 커스텀으로 만든 노션 MCP의 장점이 뭐냐면:

예를 들면 '회의록 불러오기' 기능 같은 거 있잖아요. 노션 MCP를 그냥 쓰면 먼저 목록을 불러온 다음에 그 툴이 목록을 불러오는 툴이 있고 그 목록에서 페이지 하나하나 불러오는 툴이 따로 있어요.

내가 만약에 관련된 회의록이 여섯 개다 그러면 목록 한번 불러오고 회의록을 여섯 번 불러와서 총 **일곱 번의 툴 호출**이 필요하거든요.

근데 커스텀 MCP를 만들면 그냥 '관련 회의록 불러오기' 툴을 만들어서 **툴 호출 한 번**에 그걸 끝낼 수 있어요.

커스텀 MCP를 만들면 내 워크플로에 맞춰서 그냥 툴을 합쳐버릴 수가 있어요.

## 계정 분리 시 연속성 확보

Claude Code 계정을 여러 개 쓰면 작업의 연속성은 어떻게 확보하나요?

그래서 **중간 마크다운**을 쓰는 거예요. 얘가 Spec Writer하고 Document를 쓰잖아요. 그러면 이 Document를 쓰기 전 과정은 남길 필요가 없어요. **Document만 남으면** 되거든요.

그러니까 이 페이지와 이 페이지가 서로 다른 계정을 쓰고 있어도 상관없어요. 이런 식으로 **페이지를 나누면** 요런 장점이 있습니다.

그리고 Implement를 만약에 하다가 끊겼다 그러면 플랜 문서가 명확히 있었으니까 다시 시키면 돼요. "이 계획대로 구현할 건데 안 된 거 파악해서 해라."

사실 중간에 끊기는 경우는 잘 없어요. 왜냐하면 좀 간당간당하다 싶으면 계정 옮기라고 가이드를 드렸거든요.

## 프론트엔드/백엔드 작업 순서

바이브 코딩할 때 프론트부터 하세요 백엔드부터 하세요 하는데, 저는 **기능 단위로 묶어서 같이** 해요.

그래서 그렇게 하시는 걸 추천드려요. 레포지터리 좀 묶어놓고 그러니까 프론트엔드 백엔드 코드베이스 분리돼있어도 좀 모노레포 같은 걸로 묶어놓고 같이 한 번에 작업되도록 하면요.

예를 들면 제가 부스터에 댓글 기능을 추가한다고 해보죠. 그러면 그 기능을 추가하기 위해서 프론트 작업도 해야 되고 백엔드 작업도 해야 되잖아요. 그거를 그냥 **한 번에 한 번에 프롬프트로 시켜요**.

근데 구현은 백엔드부터 하죠. 구현은 DB부터 시작해서 에이전트가 내부적으로 DB부터 하고 백엔드 하고 프론트엔드 하도록 가이드는 하는데 프롬프트는 한 번만 합니다.

## 데우스(Deus) 프로젝트 소개

지금 만드는 프로젝트를 여기서 처음 공개하는 건데요, 이런 걸 만들고 있습니다.

저는 **다음 세대 IDE**가 필요하다고 생각해요. Cursor나 Windsurf의 불만이 VS Code에 AI 기능을 더한 거잖아요. 근데 이거 자체가 좀 웃겨요. 왜냐하면 VS Code 자체가 개발자가 손으로 작업하는 걸 기준으로 디자인된 도구인데, 거기에 AI 기능을 얹는 게 아니라 그냥 **AI로 작업하는 것만을 위한 코딩 도구**가 있어야 된다고 전 생각을 하거든요.

저는 제가 제 시간을 어디에 가장 많이 뺏기고 있나를 좀 돌이켜보니까 **코딩 에이전트를 위한 컨텍스트를 설정하고** 코딩 에이전트의 입맛을 맞춰주는데 좀 제 시간을 다 쓰고 있더라고요. Claude Code에 필요한 막 서브 에이전트 만들고 막 이겨야 한다 이러면서 막 만들고 있는 거죠.

근데 이게 좀 상하 관계가 역전된 거 같지 않나요? 왜냐하면 코딩 에이전트를 위해서 저희가 봉사하는 느낌. 그래서 **컨텍스트 엔지니어링을 대신해주는** 개발 환경을 만들고 싶어요 저는.

저는 목표하는 바가 뭐냐면 얘가 그냥 제가 아까 말씀드린 뭐 파이프라인이니 스킬이니 뭐 이런 거 있잖아요. 필요한 거 다 알아서 만들고 얘가 **Claude Code로 호출**하는 거예요. 그래서 코딩 에이전트도 그냥 도구인 거죠.

저는 코딩 에이전트에 여러 가지 도구를 쥐어주고 있는 게 좀 웃기는 상황이라고 생각하거든요. 왜냐하면 코딩은 개발자가 하는 일의 한 부분에 불과한데, 코딩 에이전트에 여러 개를 쥐워줘서 얘를 개발자처럼 만들 게 아니라 **개발자로서 사고하는 에이전트가 도구로서 코딩 에이전트를 호출**해야 된다고 생각해요.

그게 구조적으로 맞다고 생각을 해서 그런 역할을 하는 개발자 에이전트를 만들려고 하고 있습니다. **저를 만드는 거예요.**

관심 있으신 분들은 deus.build에서 웨이트리스트를 등록해주세요.
